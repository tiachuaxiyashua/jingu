# 从 0 开始的未来愿景脑暴

> 状态：历史脑暴素材 / 概念来源 / 非直接决策真相。
>
> 当前阶段的综合真相以 `03-超级个体外骨骼与能力集群真相.md` 为准。本文保留为第一轮发散材料和概念来源；后续若使用本文概念，应先吸收到当前真相文档中再作为重构依据。

## 0. 这不是一条固定流水线

“人类意图 -> AI 组织建制 -> 原子任务分配 -> 多模型执行 -> 对抗评审 -> 记忆沉淀 -> 组织和流程自我优化”只能作为一种例子，不能成为新的牢笼。

未来系统不应该只有一条路。它应该像一个会呼吸的外部神经系统：有时像产品经理，有时像心理咨询师，有时像刑侦专家，有时像公司，有时像实验室，有时像工厂，有时像一双安静但强壮的手。

更抽象地说，它应该做三件事：

```text
看见人类真正想要什么
  -> 调度世界上可用的智能与能力
  -> 交付一个人类能理解、能控制、能继续放大的结果
```

这份文档只负责发散，不负责定稿。

## 1. 人类不应该被迫先变成产品经理

很多用户只有痛点，没有需求；只有烦躁，没有目标；只有“哪里不对劲”的感觉，没有语言。

因此系统的第一能力不是“接收任务”，而是“意图识别”。

### 1.1 意图识别不是填表

它应该主动使用多种对话姿态：

| 姿态 | 作用 |
|---|---|
| 产品经理 | 追问用户、场景、约束、优先级、成功标准 |
| 心理咨询师式倾听 | 捕捉用户没有说清楚的焦虑、厌烦、恐惧、期待和真实动机 |
| 刑侦专家 | 从矛盾、遗漏、反复出现的细节中还原事实链 |
| 导演 | 让用户描述理想一天、失败一天、最想避免的场景 |
| 设计师 | 用类比、反例、视觉化语言帮用户靠近“想要的感觉” |
| 科学家 | 把模糊猜测变成可验证小实验 |
| 教练 | 帮用户把大愿望拆成下一步能行动的选择 |

系统应该能问：

- 你说“不顺”，具体是哪一刻开始不顺？
- 如果这个问题明天消失了，你最先注意到的变化是什么？
- 你讨厌的是流程慢、结果差、不可控，还是被迫做不擅长的事？
- 这件事像不像你过去遇到过的某种问题？
- 你更想要一个工具、一个团队、一个自动化、一个模板，还是一个能陪你长期推进的伙伴？
- 哪些事情你想亲自决定，哪些事情你只想看结果？

### 1.2 意图识别的产物

意图识别阶段不一定产出任务，它可以产出多种中间物：

- 痛点画像。
- 隐含目标。
- 真实约束。
- 用户语言到系统语言的翻译。
- 未确认假设。
- 可能方案菜单。
- 反向需求：用户明确不想要什么。
- “如果我理解对了”的复述。

这一步的目标不是快，而是准。准了以后，后面的自动化才值得跑。

## 2. 解决方案不应只等于工作流

识别意图之后，系统应该给用户一个解决方案，但这个方案不一定是 Flow。

可能的解决方案包括：

| 方案形态 | 例子 |
|---|---|
| 持续工作流 | 每周自动收集资料、总结、生成报告 |
| 一次性产出 | 需求文档、方案、代码补丁、研究报告 |
| 自动化功能 | 监听目录、整理文件、推送提醒 |
| 智能团队 | 研究员 + 架构师 + 红队 + 执行者 |
| 人类工作台 | 一个面板帮用户看见进展、风险和决策点 |
| 教学/陪练 | 引导用户学习一套能力 |
| 诊断系统 | 定期发现系统、项目、身体或工作流里的异常 |
| 市场包 | 可分享的角色、技能、流程、评估和策略组合 |
| 实验计划 | 用低成本实验验证某个方向是否值得做 |

所以系统不应该问：

```text
我要生成什么工作流？
```

而应该问：

```text
这个人类真正需要什么形态的外部能力？
```

## 3. 组织产出：像团队，也像机器，也像生物

当意图被识别后，系统需要组织产出。组织方式不应该固定。

它可以像公司：

```text
老板：人类
幕僚长：理解目标、拆解方向、协调资源
研究员：找资料和证据
架构师：设计方案
执行者：完成原子任务
红队：攻击假设
裁判：裁决争议
史官：记录决策和经验
优化器：提出流程改进
```

也可以像机器：

```text
输入感知器 -> 解析器 -> 计划器 -> 执行器 -> 校验器 -> 反馈器
```

也可以像生物：

```text
感知系统：发现变化和痛点
神经系统：理解、判断、协调
肌肉系统：调用工具和执行能力
免疫系统：识别风险、错误和越权
记忆系统：沉淀经验
进化系统：修改自己的打法
```

关键不是选一个比喻，而是允许系统按任务选择组织形态。

## 4. 原子化不是把世界切碎，而是让协作可分配

“原子任务”不是为了机械拆分，而是为了让不同能力等级的模型和工具能各干其事。

原子任务应该具备：

- 小到可以被单个模型或工具完成。
- 有明确输入。
- 有明确输出。
- 有验收条件。
- 能重试。
- 能复用。
- 能并行。
- 能标注适合小模型、中模型、大模型或规则程序。

可能的原子类型：

| 原子类型 | 适合执行者 |
|---|---|
| 抽取 | 小模型、规则程序 |
| 分类 | 小模型 |
| 格式化 | 小模型、脚本 |
| 查重 | 小模型、程序 |
| 引用核验 | 小模型、检索器 |
| 草拟 | 中模型 |
| 评审 | 中/大模型 |
| 综合判断 | 大模型 |
| 策略规划 | 大模型 |
| 工具执行 | 受控 capability |

大模型不应该被浪费在搬砖上，小模型也不应该被迫做战略判断。

## 5. 人类需要看到的不是裸链式思考，而是可用的决策轨迹

系统要让人类清楚看到：

- 过去问过什么。
- 形成了哪些假设。
- 哪些假设被证据支持。
- 做过哪些关键决策。
- 当前工作进展到哪里。
- 哪些任务正在跑。
- 哪些任务阻塞。
- 什么时候需要人类介入。
- 如果不介入，系统会怎么默认处理。

这里要避免一个误区：不应把模型的隐藏推理链原样当 UI。更合适的是展示可公开的决策轨迹：

```text
问题 -> 假设 -> 证据 -> 选择 -> 结果 -> 风险 -> 下一步
```

人类要看到的是“为什么这样做足够可信”，而不是每一个内部 token。

## 6. 简洁高效：未来感不等于复杂

真正强的系统应该是：

```text
简单入口
深层能力
渐进展开
必要时复杂
平时像一只很懂事的手
```

第一屏不应该问用户选 Flow、Role、Skill、AgentProfile。

第一屏应该问：

```text
你现在哪里卡住了？
你想让这个系统帮你放大什么能力？
你希望自己保留哪些决定？
```

复杂性应该藏在系统内部，并能在用户需要时展开。

## 7. 候选“能力原语”，不是最终分层

下面这些不是层级，只是未来系统可能需要的一组原语。

| 原语 | 解释 |
|---|---|
| Intent Probe | 主动洞察用户真实意图 |
| Possibility Engine | 生成多种解决形态，而不只生成工作流 |
| Organization Builder | 自动或人工搭建智能组织 |
| Role | 组织中的职位和责任 |
| Skill | 可迁移的方法包 |
| Capability | 可执行工具和外部能力 |
| Atomic Work | 可分配、可验收、可重试的小任务 |
| Context Pack | 本次运行所需上下文切片 |
| Decision Log | 可公开的决策链条 |
| Human Aperture | 人类介入点和授权窗口 |
| Critique Loop | 对抗、评估和修正机制 |
| Memory Garden | 可增长、可修剪、可审计的记忆 |
| Evolution Proposal | AI 对流程、技能、组织的改进建议 |
| Package | 可分享迁移的一组组织、技能、流程和策略 |

## 9. 需要从当前 AI 发展方向吸收的东西

当前值得吸收的方向包括：

- Anthropic 的 workflow / agent 区分：可预测路径和动态 agent 不应混为一谈。
- Anthropic 的 orchestrator-workers、parallelization、evaluator-optimizer：复杂任务需要动态拆分、并行执行和反馈修正。
- Anthropic Agent Skills 的渐进披露：能力包应是文件夹，先读轻量说明，需要时再读资源。
- OpenAI Agents 的 handoff、guardrail、trace 思路：智能体之间的交接、权限和可观测性应是一等对象。
- LangGraph 的 durable execution / interrupt / persistence：长任务必须能中断、恢复和追踪。
- MCP 的 tools / resources / prompts / roots 思路：外部能力和上下文边界应协议化，不应藏在 UI 状态里。

这些不是要复制某个框架，而是提醒我们：未来系统必须同时具备动态性、边界感、可恢复性和可观察性。

## 10. 反模式

需要警惕：

1. 把所有问题都变成工作流图。
2. 把角色做成 prompt cosplay，而不是组织责任。
3. 把技能做成一堆上下文文本，而不是可迁移能力包。
4. 把记忆做成聊天记录，而不是可审计知识资产。
5. 把“大模型指挥，小模型干活”做成口号，而没有原子任务和验收标准。
6. 把 UI 做成真相源，让文件只是导出结果。
7. 把自动化当成目标，而不是人类能力放大的副产品。
8. 为了未来感而堆复杂度，忘了用户最先需要的是“被理解”。

## 11. 当前最值得继续脑暴的问题

1. 如何判断一个用户只是需要一次性产出，还是需要长期外骨骼？
2. Intent Probe 应该如何主动，但不冒犯、不操控？
3. 什么样的组织可以自动生成，什么必须由人类批准？
4. 原子任务的最小通用协议是什么？
5. 小模型适合的任务边界如何自动判断？
6. 记忆何时自动沉淀，何时必须请求批准？
7. 如何让用户看到“决策轨迹”，但不暴露或伪造隐藏推理链？
8. 一个能力包如何做到足够可迁移，又不变成沉重框架？
9. 系统如何知道自己这次做得不好，并提出自我改进？
10. 人类作为“老板和灵魂”时，最小但足够的控制台应该长什么样？

## 12. 暂时的北极星

这个系统不是工作流编辑器，不是聊天机器人，不是自动化平台，也不是一家公司模拟器。

更接近的说法是：

```text
一个文件原生的意图放大器。
它主动理解人类模糊的痛点，
组织可迁移的智能与工具，
交付可观察、可控制、可复盘的结果，
并在人的授权下持续长出新的能力。
```

如果最后它真的成功，用户不需要先学会如何给 AI 下精确任务。

用户只需要带着一个模糊但真实的痛点走进来，系统会和他一起把那个痛点变成杠杆。
