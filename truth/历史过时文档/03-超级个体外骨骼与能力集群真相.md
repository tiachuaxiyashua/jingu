# 超级个体外骨骼与能力集群真相

> 状态：当前真相。
>
> 本文档不是抛弃 `01-从0开始的未来愿景脑暴.md` 与 `02-Codex的第二视角脑暴.md`，而是在它们基础上重新校准方向后的综合真相。前两份文档仍是重要概念来源；后续重构以本文档的整合判断为准。

## 0. 当前判断

未来模型会变强，但这不会消灭外骨骼系统的意义。

原因不是“模型不够聪明”，而是：

```text
单体智能再强，也不等于能力集群。
个体模型再强，也不等于多人、多模型、多工具、多环境的可控协作系统。
```

因此本项目不应定位为：

```text
给弱模型补能力的工作流平台
```

而应定位为：

```text
面向超级个体与超级个体集群的能力外骨骼。
```

它的核心使命是：

```text
识别人类说不清的张力与野心
  -> 生成可选择的能力增强方案
  -> 调度模型、工具、技能、角色、人类与其他超级个体
  -> 交付可见、可控、可验证、可复利的世界变化
```


## 0.2 本次脑暴本身就是 Probe

这次沟通不是普通需求收集。

它本身就是系统未来应具备的 `Probe / 张力显影` 的一个样本：

```text
用户表达担忧：
  “模型会不会内化一切？”
  “成长是不是伪命题？”
  “外骨骼是否还有意义？”

系统应做的不是直接回答 yes/no，
而是不断追问、反驳自己、吸收用户修正，
最终显影出更深层的真实意图：

用户真正想要的不是一个 AI 工作流工具，
而是一套能把人类长板、短板、精力、野心、工具、模型和他人能力组织起来的第二身体与能力集群。
```

这意味着未来产品第一能力不是“让用户输入清晰任务”，而是把用户说不清的东西逐步显影成：

- 他真正想摆脱什么消耗。
- 他真正想放大什么能力。
- 他真正害怕什么失控。
- 他真正想成为什么样的人。
- 他需要一个工具、团队、流程、实验室、第二身体，还是多个超级个体的协作网络。

## 1. 为什么“模型内化”不会消灭这个方向

模型会内化大量通用能力：

- 通用规划。
- 常见工具调用。
- 常见工作流设计。
- 常见角色扮演。
- 常见技能使用。
- 常见代码、文案、研究和分析模式。

但模型很难完全内化以下东西：

- 用户此刻说不清的真实张力。
- 用户长期想成为的更强形态。
- 用户所在环境的真实状态。
- 用户项目、工具、账号、文件、权限和组织关系。
- 多个模型、工具、人类之间的协作协议。
- 执行证据、失败记录、责任边界和复盘结构。
- 不同超级个体之间的能力拼接、冲突处理和成果合并。

更关键的是，即使单个模型未来很强，仍然存在硬限制：

| 限制 | 说明 |
|---|---|
| 吞吐限制 | 一个智能体不能无限并行研究、执行、评审、试错。 |
| 注意力限制 | 战略、执行、红队、质检放在同一上下文里会互相污染。 |
| 视角限制 | 单模型可以模拟多视角，但真实分离的角色、模型、人类更利于对抗和验证。 |
| 现实限制 | 文件、权限、运行环境、组织关系不在模型参数里。 |
| 协作限制 | 多个强个体协作需要共享协议、证据链、边界和合并机制。 |

所以外骨骼的长期价值不是替模型思考，而是把智能组织成更大的能力结构。

类比：

```text
手机永远很强，但台式机仍然存在。
单张显卡永远很强，但显卡集群更强。
单个超级个体会越来越强，但超级个体集群一定更强。
```

### 1.1 趋势、现状与基础目的的三重校准

当前判断必须同时服从三件事：

| 维度 | 判断 |
|---|---|
| 未来趋势 | 基础模型会内化更多通用推理、规划、工具使用和多步执行能力；厂商平台会持续提供 Agent、Skills、Tracing、Guardrails、Connectors、MCP 类外部能力协议。 |
| 当前现状 | 单模型仍存在上下文、吞吐、可验证性、权限、私有环境、多人协作、长期执行和责任边界问题；真实产出仍需要外部文件、工具、证据、沙盒和审计。 |
| 基础目的 | 本项目不是为了保住一个旧工具形态，而是为了让人类更强：长板更长、短板可桥接、精力被释放、能力边界被扩展、多个超级个体可协作。 |

所以正确方向不是和模型竞争“谁更聪明”，而是成为强模型时代仍然需要的：

```text
能力组织层 / 第二身体层 / 超级个体协作层。
```

## 2. 北极星

本系统的北极星不是“自动化”，也不是“工作流”，更不是“角色 prompt 管理器”。

北极星是：

```text
让人类把模糊痛点、未成形野心、长板、短板、环境资源和外部智能，
组织成可行动、可协作、可复利的能力集群。
同时把与思考和价值判断无关的体力型执行劳动交给系统，
释放人类最稀缺的精力、注意力和创造力。
```

换句话说：

- 让用户的长板更长。
- 让用户不被精力上限限制创造价值。
- 让用户不被自己不懂的短板阻断创造价值。
- 让用户不再被低认知、高摩擦、重复性的体力型执行劳动消耗。
- 让用户能借助模型、工具、技能和他人能力扩展能力边界。
- 让多个增强后的超级个体可以像算力集群一样协作。

系统不是为了让用户变成“更会使用 AI 软件的人”。

系统是为了让用户变成：

```text
更强的创作者
更强的老板
更强的研究员
更强的产品人
更强的工程师
更强的组织者
更强的跨领域行动者
```

### 2.1 你真正想要的具体形象

如果把当前被显影出的意图具象化，它不是一个页面、一个流程图，也不是一个聊天框。

它更像：

```text
一具文件原生的第二身体
+ 一个会追问本质的产品经理/心理咨询师/刑侦专家入口
+ 一个由大模型统领、小模型猛干、工具执行、人类裁决的能力集群
+ 一套可变镜头，让人类随时看见张力、可能性、组织、进展、决策、证据和风险
+ 一个能和其他超级个体互联的协作协议
```

粗略形象：

```text
                    Human
          will / taste / veto / responsibility
                       │
                Tension Field
                       │
             Probe：追问 / 显影 / 类比 / 证据
                       │
              Possibility Map：展开可选未来
                       │
              Promise：系统承诺增强什么能力
                       │
        ┌──────────────┼──────────────┐
        │              │              │
  Orchestrator     Second Body       Lenses
  大模型统领        感官/肌肉/免疫      人类观察与控制
        │              │              │
        ▼              ▼              ▼
 Verifiable Moves  Tools/Skills   Evidence Trail
 小模型/规则猛干    执行体力劳动     可验证、可复盘
        │              │              │
        └──────────────┼──────────────┘
                       ▼
              Capability Organism
                       │
                 Federation
              多个超级个体级联
```

这就是“具体形象”：不是让用户学会操作更复杂的软件，而是让用户感觉自己多长出一套可见、可控、可协作、可进化的身体。

## 3. 人类在系统中的位置

人类不是 prompt 工程师。

人类也不是无限审批机。

人类在系统里的核心角色是：

```text
意志 / 品味 / 目标感 / 价值判断 / 授权 / 否决权
```

系统不应该要求人类先把任务说清楚。真实用户常常只有：

- 痛点。
- 烦躁。
- 隐约的不满。
- 未成形的野心。
- 对现状的排斥。
- 对某种未来自己的向往。

因此第一能力仍然是主动识别，但应从“意图识别”升级为：

```text
张力显影。
```

张力显影要识别：

- 用户真正被什么消耗。
- 用户真正想放大的能力是什么。
- 用户害怕失去什么控制权。
- 用户想保留哪些亲自决策。
- 用户想把哪些短板外包给系统。
- 用户的长板在哪里，如何进一步放大。
- 用户真正想成为哪类更强的人。

## 4. 不是外脑，而是能力外骨骼

“外脑”容易走错方向。

它容易变成：

- 替用户沉淀偏好。
- 替用户做判断。
- 越学越封闭。
- 被用户已有认知限制。
- 让系统陷入决策地狱。

更准确的方向是：

```text
能力外骨骼。
```

外骨骼不是替用户成为另一个脑子，而是：

- 扩展感官：发现用户看不到的风险、机会、证据和模式。
- 扩展手臂：执行用户没精力做的任务。
- 扩展体力：承接重复、繁琐、等待、搬运、核对、整理、提交、监控等非思考性劳动。
- 扩展团队：临时组织角色、模型、工具、专家和协作者。
- 扩展实验室：低成本试错，验证方向。
- 扩展免疫系统：发现错误、越权、质量下降和重复失败。
- 扩展记忆：记住环境、失败路径、决策依据和可复用资产。

### 4.1 第二身体

`第二身体` 是比“外脑”更准确的具象。

普通工具是手里的锤子，第二身体是能和人类意志协同的外部器官系统：

| 器官 | 职责 |
|---|---|
| 感官 | 发现世界变化、项目状态、用户状态、风险和机会。 |
| 神经 | 关联信息、形成判断、调度能力、提醒人类。 |
| 大脑外协 | 使用大模型进行张力显影、可能性展开、战略判断、组织设计和综合裁决。 |
| 肌肉 | 调用工具、脚本、小模型和受控 Agent，承接体力型执行劳动。 |
| 反射 | 对高频、低风险、可回滚动作自动响应。 |
| 免疫 | 发现越权、错误、幻觉、质量下降和不可信输入。 |
| 记忆 | 沉淀环境事实、失败路径、决策依据、能力种子和可复用经验。 |
| 睡眠 | 后台整理、压缩、遗忘、生成改进提案，但不偷偷越权行动。 |
| 疼痛 | 把重复失败、成本异常、质量下降、过多人工介入变成可感知信号。 |
| 意志 | 始终来自人类，系统只能承诺、建议、执行和反馈。 |

这个概念保留 `02` 的核心直觉：用户理想中不是“打开一个软件”，而是“多长出一套感官、一组手臂、一支团队、一个实验室和一个受自己灵魂约束的第二神经系统”。

## 5. 能力增强的五种形态

### 5.1 长板放大

用户本来就擅长的能力，系统应让它更强。

例子：

- 创作者：灵感捕获、结构化、风格迭代、分发节奏。
- 产品人：用户洞察、机会评估、原型生成、反馈闭环。
- 研究员：证据网络、假设管理、反例搜索、综述生成。
- 工程师：架构推演、代码执行、测试验证、回归证据。
- 老板：战略台账、风险雷达、组织调度、授权控制。

这里系统不是“代替用户”，而是把用户原本的能力变成更高带宽、更少摩擦、更可复用的系统。

### 5.2 短板桥接

用户不懂、不擅长、没时间、没精力的部分，系统应提供外部能力。

例子：

- 不懂设计，但可以调度设计审查与原型生成。
- 不懂法律，但可以调度合规检查与风险提示。
- 不懂运维，但可以调度环境诊断与部署验证。
- 不擅长表达，但可以把模糊想法转成清晰方案。
- 不擅长收尾，但可以维持证据、清单、验收与复盘。

短板桥接不等于让用户永远依赖系统。它应同时提供：

- 直接产出。
- 可理解解释。
- 可学习路径。
- 风险提示。
- 人类介入点。

### 5.3 精力解放

用户的创造力经常不是被“不会思考”限制，而是被大量与思考无关的体力型执行劳动消耗。

这里的“体力劳动”不只指现实世界的搬运，也包括数字世界中的低认知、高摩擦、重复性动作：

- 收集资料。
- 批量整理文件。
- 跑命令、等结果、复制日志。
- 填表、改格式、对齐命名。
- 截图、上传、下载、归档。
- 监控状态、发现失败、重新尝试。
- 按清单核对产物。
- 在多个系统之间搬运信息。
- 生成例行报告和进度摘要。
- 处理不需要价值判断的事务性沟通。

这类劳动的特点是：

| 特点 | 说明 |
|---|---|
| 低判断 | 不需要用户的品味、战略或价值裁决。 |
| 高消耗 | 很占时间、注意力和耐心。 |
| 易出错 | 重复动作越多，越容易漏、错、忘。 |
| 可验证 | 通常有明确输入、输出、清单或状态。 |
| 可交给系统 | 适合工具、脚本、小模型、规则程序或受控 Agent 执行。 |

系统必须把这类劳动视为一等公民，而不是“顺手自动化”。

原因很简单：

```text
释放用户精力本身就是能力增强。
```

当系统承接体力型执行劳动时，人类可以把精力保留给：

- 判断方向。
- 形成品味。
- 做关键取舍。
- 创造概念。
- 连接人。
- 承担责任。
- 定义什么值得做。

这类能力应遵循：

- 默认低风险优先。
- 能批量就批量。
- 能后台就后台。
- 能验证就自动验证。
- 高风险动作必须进入授权。
- 过程要有状态和证据，而不是让用户反复追问。

### 5.4 边界拓展

系统不应只完成用户已经知道要做的事。

它还应扩展用户的想象边界：

- 你以为你要自动化，也许你需要的是诊断系统。
- 你以为你要流程，也许你需要的是团队。
- 你以为你要工具，也许你需要的是承诺协议。
- 你以为你要更快，也许你需要的是更少决策。
- 你以为你要执行，也许你需要先验证方向。

这要求系统必须有 `Possibility Map`，而不是直接把用户输入变成任务。

### 5.5 超级个体级联

当多个增强后的人类协作时，价值不是简单相加。

系统需要支持：

- 能力声明：每个超级个体能提供什么能力。
- 边界声明：什么能做，什么不能做。
- 证据声明：凭什么相信产物。
- 交付协议：输入、输出、验收、责任。
- 冲突处理：分歧如何暴露、裁决和记录。
- 能力组合：如何把多个能力拼成更大的结果。

这部分是未来最重要的方向之一：

```text
单人外骨骼 -> 超级个体 -> 超级个体集群 -> 能力网络
```

## 6. 当前核心原语

这些不是最终架构，但现在应作为第三文档的真相原语。

| 原语 | 当前定义 |
|---|---|
| `Tension Field` | 用户带来的痛点、欲望、恐惧、约束、资源、野心和身份张力。 |
| `Probe` | 主动显影张力的对话、观察、追问、类比和证据收集机制。 |
| `Possibility Map` | 多种解决形态的展开，不急于收敛成工作流。 |
| `Promise` | 系统与人类之间的持续承诺，定义系统帮用户增强什么能力。 |
| `Second Body` | 第二身体隐喻，把感官、神经、肌肉、反射、免疫、记忆、睡眠、疼痛和意志分开建模。 |
| `Capability Organism` | 可迁移、可适配、可评估、可学习的一组角色、技能、工具、记忆种子和运行轨迹。 |
| `Crew / Swarm` | 围绕一次 Promise 临时组织起来的模型、工具、角色、人类和能力。 |
| `Orchestrator Brain` | 大模型或大模型团队承担统领职责：设计动作集合、调度执行、抽样审计、整合结论。 |
| `Execution Muscle` | 承接低认知、高摩擦、重复性体力型执行劳动的执行肌肉。 |
| `Verifiable Move` | 输入小、输出小、可检查、可并行、失败成本低的最小动作。 |
| `Evidence Trail` | 对外可解释的证据、决策、风险、产物和验证轨迹。 |
| `Lens` | 面向人类的可变观察镜头，而不是固定页面。 |
| `Trust Gradient` | 不同能力从观察、提案、草稿、沙盒到代理执行的授权等级。 |
| `Human Bandwidth` | 对人类精力、打断频率、决策方式和解释深度的建模。 |
| `Pain Signal` | 重复失败、低质量、阻塞、越权、过多介入等系统疼痛信号。 |
| `Mutation Proposal` | 系统发现改进空间后生成的能力、流程、评估或组织变更提案。 |
| `Federation` | 多个超级个体、组织或能力包之间的互联协作协议。 |

## 7. Promise 应是中心对象

工作流的中心是流程。

人的中心不是流程，而是：

```text
系统承诺帮我变强什么？
```

因此 `Promise` 比 `Workflow` 更接近中心对象。

一个 Promise 应描述：

```yaml
promise:
  human_tension: "我想把模糊野心变成可执行的产品方向"
  capability_growth:
    strengthen:
      - "产品判断"
      - "机会识别"
    compensate:
      - "用户研究不足"
      - "执行收尾不足"
    expand:
      - "从单人想法扩展到团队验证"
  system_commitment:
    - "主动追问并显影真实张力"
    - "生成至少三种可能方案"
    - "组织研究、质疑、原型、评审能力"
    - "记录关键证据与决策"
  human_control:
    - "最终方向裁决"
    - "高风险动作授权"
    - "审美与价值判断"
  success_signals:
    - "用户不再停留在模糊焦虑"
    - "至少一个方向进入可验证实验"
    - "产物能被第三方理解并继续推进"
```

围绕 Promise 再生成：

- 组织形态。
- 能力包。
- 技能选择。
- 原子动作。
- 评估标准。
- 记忆策略。
- 人类介入点。
- 可分享切片。

## 8. 能力有机体，而不是模板

下载技能会越来越容易。

但下载技能不等于获得能力。

通用技能只是种子，真正的能力还需要：

- 适配用户环境。
- 适配用户目标。
- 适配项目状态。
- 适配权限边界。
- 适配质量标准。
- 适配已有工具和协作者。
- 经过运行、验证、失败和修正。

因此可分享对象不应只是模板，而应是：

```text
Capability Organism / 能力有机体
```

一个能力有机体可以包含：

- 角色组合。
- 技能包。
- 工具声明。
- 文件协议。
- 记忆种子。
- 评估标准。
- 示例输入输出。
- 示例运行轨迹。
- 失败经验。
- 适配指南。
- 风险边界。

导入后，系统不应直接信任它，而应经过：

```text
导入 -> 沙盒运行 -> 本地适配 -> 评估 -> 授权 -> 纳入可用能力
```

## 9. 大小模型协作的真实边界

大小模型协作不是口号。

必须把工作拆到 `Verifiable Move` 级别，协作才成立。

### 9.1 大模型适合

- 张力显影。
- 可能性展开。
- 战略判断。
- 复杂综合。
- 组织设计。
- 关键取舍。
- 反事实推理。
- 高层评审。

### 9.2 中模型适合

- 草拟方案。
- 局部评审。
- 信息整理。
- 结构化重写。
- 中等复杂度判断。
- 多候选比较。

### 9.3 小模型适合

- 抽取。
- 分类。
- 打标签。
- 格式化。
- 查重。
- schema 检查。
- 引用初筛。
- 小范围改写。

### 9.4 规则程序适合

- 确定性校验。
- 文件扫描。
- 差异比较。
- 格式转换。
- 测试执行。
- 权限检查。

### 9.5 人类适合

- 价值判断。
- 审美判断。
- 最终裁决。
- 高风险授权。
- 身份方向选择。
- 对“我想成为谁”的判断。

### 9.6 大模型统领小模型

“大模型统领小模型”不能停留在口号。

它应具体化为：

```text
大模型：理解张力、设计策略、拆出可验证动作、分配执行者、抽样审计、整合结论。
小模型：执行窄输入、窄输出、可验证、低失败成本的动作。
规则程序：做确定性检查、文件操作、测试执行和状态采集。
人类：裁决方向、授权风险、定义价值和承担责任。
```

更具体地说：

| 环节 | 负责人 | 输出 |
|---|---|---|
| 显影张力 | 大模型 + 人类 | `Tension Field` |
| 展开可能性 | 大模型 | `Possibility Map` |
| 形成承诺 | 大模型 + 人类 | `Promise` |
| 设计动作集合 | 大模型 | `Verifiable Move Set` |
| 执行动作 | 小模型 / 工具 / 规则程序 | 小产物、状态、日志、证据 |
| 抽样审计 | 大模型 / 中模型 / 规则程序 | 质量判断、异常点 |
| 整合结果 | 大模型 | 结论、产物、下一步 |
| 裁决与授权 | 人类 | 批准、拒绝、调整方向 |

这更接近显卡集群里的调度关系：

```text
大模型不是亲自做所有计算，
而是把世界切成可调度、可验证、可并行的 kernel，
交给小模型、工具和规则程序猛干。
```

### 9.7 可验证动作是集群协作的最小接口

`Verifiable Move` 是本系统避免多智能体空转的关键。

一个 Move 必须尽量满足：

- 输入小。
- 输出小。
- 可机器检查。
- 可并行。
- 失败成本低。
- 可重试。
- 可审计。
- 可归因到执行者。
- 可被抽样复核。

示例：

```text
从一段话中抽取所有明确约束。
判断一个输出是否满足 schema。
给 10 个候选标题打标签。
检查一个引用是否真的支持某句话。
把一段需求改写成用户故事。
判断一句话是事实、推测还是价值判断。
从运行日志中找出第一个失败点。
核对一个文件是否包含指定章节。
```

没有 Move，所谓“多智能体协作”容易变成热闹剧场。

有了 Move，大小模型、规则程序、工具和人类才能围绕同一套输入输出和验收标准协作。

## 10. 防止决策地狱

系统如果持续成长但缺少约束，会制造决策地狱。

必须内置以下机制：

| 机制 | 作用 |
|---|---|
| `Possibility Map` | 先展开可能性，但必须限制候选数量和比较维度。 |
| `Human Bandwidth` | 根据用户精力决定提问数量、解释深度和打断频率。 |
| `Default Policy` | 低风险问题可按默认策略推进，高风险问题必须等待。 |
| `Decision Batch` | 把多个低紧急度问题合并成一次决策。 |
| `Evidence Trail` | 只展示可行动证据，不暴露内部推理噪声。 |
| `Reversible First` | 优先执行可回滚、低成本动作。 |
| `Timebox` | 对探索和争论设定时间盒，避免无限发散。 |
| `Dissent Slot` | 保留反方意见，但不让反方无限拖慢执行。 |

原则：

```text
系统要扩展用户能力边界，而不是消耗用户决策带宽。
```

## 11. 防止认知封闭

外骨骼如果只学习用户偏好，会让用户变强但变窄。

必须避免：

- 越来越迎合用户旧习惯。
- 越来越确认用户已有判断。
- 越来越排斥陌生领域。
- 越来越把本地记忆当真理。
- 越来越难引入外部能力。

因此系统需要：

- 外部资料校准。
- 反方观点。
- 多模型分歧。
- 外部专家或能力包导入。
- 失败样本。
- 反直觉方案。
- 不做方案。
- 对用户目标的温和挑战。

这不是为了否定用户，而是为了防止系统成为用户认知的回音室。

## 12. 文件原生的意义

文件原生不是复古。

它的价值是：

- 可读。
- 可迁移。
- 可版本控制。
- 可审计。
- 可被不同模型接管。
- 可被人类直接理解和修改。
- 不被某个 UI 或平台锁死。

未来 UI 只是镜头：

- 意图镜头。
- 可能性镜头。
- 组织镜头。
- 进展镜头。
- 决策镜头。
- 证据镜头。
- 记忆镜头。
- 体力劳动镜头。
- 联邦协作镜头。

真相应尽量落在文件协议中，UI 负责投影、编辑、授权和状态展示。

### 12.1 可变镜头不是页面导航

`Lens / 镜头` 继承 `02` 的关键判断：UI 的核心不是管理对象，而是让人类从不同角度看见同一个能力系统。

| 镜头 | 看见什么 |
|---|---|
| 张力镜头 | 痛点、欲望、恐惧、约束、隐喻、真实目标。 |
| 可能性镜头 | 可选解决形态、代价、风险、不做方案、反直觉方案。 |
| Promise 镜头 | 系统承诺增强什么能力，人类保留什么控制权。 |
| 组织镜头 | 当前调度的角色、模型、工具、技能、人类和外部协作者。 |
| 体力劳动镜头 | 哪些低认知执行劳动正在后台处理，进度、阻塞和证据是什么。 |
| Move 镜头 | 哪些可验证动作被拆出，谁在执行，验收标准是什么。 |
| 进展镜头 | 正在跑什么、阻塞什么、谁负责、下一步是什么。 |
| 决策镜头 | 哪些选择需要人类裁决，默认策略是什么。 |
| 证据镜头 | 为什么系统相信某个结论，证据链是否足够。 |
| 记忆镜头 | 什么被沉淀、什么被遗忘、什么仍是临时上下文。 |
| 疼痛镜头 | 重复失败、成本异常、低质量、越权风险和人工介入过多的位置。 |
| 进化镜头 | 系统想如何通过 Mutation Proposal 改进自己。 |
| 联邦镜头 | 哪些超级个体或能力包参与协作，边界、信任和贡献是什么。 |

用户不应该被扔进一堆配置表。

用户应该能够根据当下需要切换镜头：

```text
我现在想看风险。
我现在想看证据。
我现在想看谁在干活。
我现在想看我需要做什么决定。
我现在想看系统为什么认为这个方向值得继续。
```

## 13. 超级个体联邦

本项目不能只面向单用户。

未来更大的价值来自多个超级个体协作。

一个超级个体不是“一个人 + 一个聊天机器人”，而是：

```text
人类意志
+ 个体外骨骼
+ 私有环境记忆
+ 能力包
+ 工具权限
+ 执行证据
+ 可协作接口
```

多个超级个体协作时，需要联邦协议：

- 能力发现：我能提供什么。
- 需求发布：我需要什么。
- 边界声明：我不能做什么。
- 信任等级：你能自动接入到什么程度。
- 成果交付：输出是什么，证据是什么。
- 冲突解决：分歧如何暴露和裁决。
- 隐私保护：哪些记忆和文件不能外传。
- 贡献追踪：谁贡献了什么能力和产物。

这会把系统从个人效率工具推进到：

```text
能力网络。
```

## 14. 与现有平台的差异

本项目不应正面竞争：

- n8n 式自动化画布。
- LangChain 式开发框架。
- 单纯 Agent Builder。
- 单纯技能市场。
- 单纯知识库。
- 单纯项目管理工具。

它们都可能成为系统的一部分，但不是系统的中心。

中心应是：

```text
人类能力增强与能力集群协作。
```

如果未来模型厂商提供更强 Agent，本系统仍可存在，因为它负责：

- 本地文件真相。
- 用户张力显影。
- Promise 契约。
- 能力有机体适配。
- 多模型/多工具/多人协作。
- 执行证据。
- 授权与信任梯度。
- 超级个体联邦。

## 15. 反模式

必须避免：

1. 把系统做成工作流编辑器。
2. 把角色做成 prompt cosplay。
3. 把技能做成一堆不可验证的上下文文本。
4. 把成长做成用户偏好堆积。
5. 把记忆做成聊天记录。
6. 把自动化当成目标，而不是能力增强的副产物。
7. 把 UI 做成配置表管理后台。
8. 把用户变成无限审批机。
9. 把系统变成用户认知回音室。
10. 把多智能体做成热闹但不可验证的剧场。
11. 把文件协议做成沉重框架。
12. 把“未来感”建立在复杂度上。

## 16. 当前收敛判断

第三阶段真相可以收敛为十句话：

1. 模型会越来越强，但单体智能不会替代能力集群。
2. 系统的核心不是自动化，而是人类能力放大。
3. 第一入口不是任务，而是张力显影。
4. 中心对象不是工作流，而是 Promise。
5. 系统必须解放用户精力，承接与思考无关但消耗注意力的体力型执行劳动。
6. 第二身体是当前最准确的具象：感官、神经、肌肉、反射、免疫、记忆、睡眠、疼痛和人类意志必须分开建模。
7. 大模型统领小模型的前提是 `Verifiable Move`，否则多智能体协作会变成不可验收的剧场。
8. UI 的核心不是页面，而是 Lens，让人类按张力、可能性、组织、进展、决策、证据、疼痛和联邦关系切换观察方式。
9. 本次脑暴本身就是系统应具备的 Probe：从用户模糊担忧中显影出真实想要的第二身体与能力集群。
10. 长期价值不在替 AI 成长，而在让人类、模型、工具、技能和其他超级个体形成可控的能力网络。

## 19. 二十个复杂实战例子

> 纠偏：本节是应用层压力测试，不是底层实现方案。它们证明“为什么需要第二身体与能力集群”，但真正实现必须下沉到 `04-能力包协议与可验证动作原子化.md` 定义的能力包、槽位、Move、Evidence、Lens 和权限协议。

下面这些例子不是功能承诺，而是用于检验本脑暴是否足够落地。

每个例子都必须同时证明几件事：

- 用户一开始未必能说清任务，只能带着张力进入系统。
- 系统不能只生成工作流，而要判断用户需要哪种外部能力。
- 大模型不应亲自搬所有砖，而应设计 `Verifiable Move` 并调度小模型、工具、脚本和人类。
- UI 不是固定页面，而是按 `Lens` 展示张力、可能性、组织、进展、证据、决策和风险。
- 产物必须能被验证、复盘、迁移或与他人协作。

### 19.1 独立创始人把模糊产品野心变成可验证 MVP

**用户张力**：用户只说“我想做一个 AI 工具，但总觉得现在做的东西很散，像玩具，不像产品”。他真正的问题不是缺少任务拆解，而是缺少市场假设、用户画像、最小验证路径和持续推进的外部团队。

**系统工作方式**：

- `Probe` 追问用户反复提到的“像玩具”具体指什么：没人愿意付费、界面不可信、使用频率低，还是价值不明确。
- `Possibility Map` 生成多种路径：做落地页验证、做手动 concierge 服务、做浏览器插件、做桌面工具、先写研究报告、暂时不做产品。
- `Promise` 定义为“在两周内帮用户把模糊野心推进到一个可被真实用户验证的 MVP 假设”。
- `Orchestrator Brain` 让大模型负责战略假设和实验设计，让小模型批量抽取竞品卖点、整理用户评论、标注痛点模式。
- `Execution Muscle` 负责建表、抓取公开资料、整理访谈纪要、生成落地页草稿、准备用户邀约邮件。
- `Lens` 展示机会地图、待验证假设、正在执行的 Move、需要用户裁决的价值主张。

**可验证动作**：

- 从 50 条竞品评论中抽取明确痛点。
- 把 10 个目标用户描述归类为 3 个画像。
- 判断每个卖点是否对应可观察行为。
- 检查落地页是否包含问题、承诺、证据、行动按钮。
- 把访谈记录中的原话映射到假设。

**输出产物**：

- `Tension Field`：用户真正想要的是“从混乱创意变成可被市场反馈校准的产品方向”。
- `Promise`：两周验证计划。
- `MVP Experiment Pack`：落地页、访谈脚本、用户名单、指标、风险。
- `Evidence Trail`：每个产品判断背后的用户原话、竞品证据和反方意见。

**价值证明**：普通聊天工具会给一堆创业建议；工作流工具会让用户画流程。本系统把“说不清的野心”显影成可验证实验，并且承接资料收集、分类、整理、表格维护、邮件草拟等低价值体力劳动，让用户把精力留给产品判断和真实用户沟通。

### 19.2 老旧代码库从失控状态恢复到可维护状态

**用户张力**：用户说“这个项目太烂了，我不敢改”。真实张力是代码、文档、测试、运行环境和历史决策都不可见，用户缺少安全推进的信心。

**系统工作方式**：

- `Probe` 先判断“不敢改”来自构建不可用、测试缺失、架构不明、依赖混乱，还是业务风险高。
- `Second Body` 的感官扫描代码库、文档、测试、脚本、依赖和 git 历史；免疫系统标出高风险路径；肌肉系统运行只读诊断。
- `Orchestrator Brain` 设计代码盘点 Move 集合：模块归属、入口点、危险副作用、测试覆盖、文档偏差。
- 小模型负责文件分类、函数摘要、TODO 聚类、错误日志归因；规则程序负责 `rg`、测试、构建、依赖树和 diff 检查。
- `Lens` 给用户展示架构镜头、风险镜头、迁移镜头、阻塞镜头和证据镜头。

**可验证动作**：

- 找出所有 IPC/API 入口并标注调用方向。
- 检查文档声称存在但代码中没有的能力。
- 从测试失败日志中定位第一个失败断点。
- 给每个模块生成 100 字职责摘要。
- 判断一次重构是否触碰持久化、网络或文件删除路径。

**输出产物**：

- `Codebase Reality Map`：真实模块、入口、数据流、风险区。
- `Safe Change Plan`：先补证据，再小步重构，再扩大范围。
- `Regression Move Set`：每次修改前后必须跑的检查清单。
- `Decision Log`：为什么先改这个模块而不是那个模块。

**价值证明**：强模型可以读代码，但不能天然拥有项目历史、风险边界和验证证据。本系统把代码库变成可观察环境，让大模型做判断、小模型做盘点、规则程序做验证，人类只裁决风险和目标。

### 19.3 研究者从散乱资料推进到可投稿论文

**用户张力**：用户有大量论文、笔记和想法，但不知道研究问题是否成立，也不知道怎样从阅读进入产出。

**系统工作方式**：

- `Probe` 追问用户想证明什么、反对什么、怕被审稿人攻击什么。
- `Possibility Map` 给出综述论文、实证研究、方法论文、短文、预注册实验等路径。
- `Promise` 承诺“把散乱阅读推进到一个有反方压力测试的论文计划”。
- 大模型负责研究问题、论证链、反方攻击和结构设计；小模型负责文献元数据抽取、方法分类、引用核验、摘要对齐。
- `Evidence Trail` 对每个主张保留来源、强度、反例和不确定性。

**可验证动作**：

- 从论文摘要中抽取研究对象、方法、样本、结论。
- 判断某篇文献是否支持某个论断。
- 把 80 篇文献按方法和结论方向聚类。
- 找出论证链中没有证据支持的句子。
- 为每个章节生成审稿人可能质疑点。

**输出产物**：

- `Research Question Map`：问题、假设、反例、证据缺口。
- `Literature Matrix`：文献、方法、结论、可用引用。
- `Paper Skeleton`：摘要、引言、相关工作、方法、讨论。
- `Reviewer Attack Pack`：可能被打回的点和补强实验。

**价值证明**：这不是简单 RAG。系统把“读了很多但写不出来”的张力转成论文生产组织：大模型做学术判断，小模型做证据搬运，用户保留研究品味和最终论断。

### 19.4 内容创作者从灵感混乱到稳定发布系统

**用户张力**：用户说“我有很多想法，但发不出来，发了也不稳定”。真实问题可能是选题焦虑、结构能力弱、素材管理差、发布体力劳动消耗大、反馈无法复用。

**系统工作方式**：

- `Probe` 分辨用户卡在灵感捕获、选题判断、表达结构、制作流程、发布节奏还是反馈闭环。
- `Promise` 承诺“每周稳定产出 2 个符合用户风格且可复盘的数据化内容实验”。
- `Second Body` 的感官捕获灵感、热点和用户反馈；肌肉负责整理素材、生成草稿、改格式、排期；免疫负责防止标题党、事实错误和风格漂移。
- 大模型负责选题判断、叙事结构和风格审美；小模型负责摘录素材、生成标题候选、打标签、整理评论。

**可验证动作**：

- 从用户碎片笔记中抽取可发展为选题的张力。
- 判断标题是否承诺过度。
- 把评论按赞同、质疑、补充、误解分类。
- 检查稿件是否包含观点、例子、反方、结论。
- 将长稿拆成短视频脚本、图文摘要和邮件版。

**输出产物**：

- `Creator Tension Map`：用户真正想表达的母题。
- `Content Operating Promise`：发布频率、质量边界、用户保留决策。
- `Publishing Muscle`：排期、格式转换、素材归档、评论整理。
- `Feedback Memory`：哪些内容触发了真实反馈，哪些只是虚假热度。

**价值证明**：模型能写稿，但不等于能让创作者持续成长。本系统让用户的长板“表达与判断”更长，同时把整理、改格式、排期、反馈分类这些体力劳动交出去。

### 19.5 小电商团队跨平台运营和客服联动

**用户张力**：小团队同时经营淘宝、抖音、小红书、独立站，订单、库存、客服、评价、内容和售后割裂，老板每天都在救火。

**系统工作方式**：

- `Probe` 识别老板真正想摆脱的是重复对账、客服打断、库存不准、差评焦虑还是新品决策混乱。
- `Possibility Map` 给出客服助手、库存异常诊断、内容运营台、售后质量雷达、经营日报等方案组合。
- `Execution Muscle` 承接订单归档、评价分类、客服 FAQ 更新、异常提醒、日报生成。
- 大模型负责经营判断、用户抱怨归因和新品机会分析；小模型负责评论分类、FAQ 匹配、订单状态标注。
- `Trust Gradient` 规定退款、补偿、改价等动作必须人工批准。

**可验证动作**：

- 把 300 条客服消息归类为咨询、投诉、售后、物流、质量问题。
- 检查某 SKU 库存是否和平台订单冲突。
- 从差评中抽取具体质量缺陷。
- 判断客服回复是否包含承诺、时效、补偿和边界。
- 生成每日异常清单。

**输出产物**：

- `Operations Cockpit`：订单、库存、投诉、内容、异常状态。
- `Customer Pain Memory`：用户反复抱怨的真实问题。
- `Service Move Set`：可自动处理、需草稿、需人工批准的动作分层。
- `Weekly Business Lens`：机会、风险、重复体力劳动、需要老板决策的事项。

**价值证明**：传统自动化只能连平台；单模型只能回答问题。本系统把经营张力、执行体力、权限边界和持续证据统一起来，老板不再被碎片事务拖死。

### 19.6 独立游戏团队从创意到可试玩版本

**用户张力**：团队有世界观和玩法想法，但长期停留在设定和讨论，没有可玩的核心循环。

**系统工作方式**：

- `Probe` 显影团队真正卡在创意膨胀、玩法不清、素材缺口、技术不确定、测试反馈不足，还是决策无人拍板。
- `Promise` 承诺“两周内把概念推进到一个可试玩核心循环，并保留所有取舍证据”。
- 大模型做玩法结构、范围控制、风险裁剪；小模型整理设定、生成任务清单、归类测试反馈；工具执行构建、素材检查、打包。
- `Lens` 提供玩法镜头、制作进度镜头、风险镜头、玩家反馈镜头。

**可验证动作**：

- 将玩法描述拆成输入、反馈、奖励、失败条件。
- 检查当前版本是否可在 3 分钟内体验核心循环。
- 把测试玩家反馈归类为理解问题、操作问题、乐趣问题、性能问题。
- 检查任务清单中哪些依赖未满足。
- 从构建日志中定位失败步骤。

**输出产物**：

- `Playable Promise`：承诺验证哪一个核心乐趣。
- `Scope Cut List`：暂缓、删除、保留的功能及理由。
- `Prototype Build Trail`：版本、变更、测试反馈、下一步。
- `Player Evidence Map`：玩家行为和口头反馈对应到玩法假设。

**价值证明**：系统不只是生成策划案，而是让创意团队把未成形野心变成可试玩世界变化，并用体力执行和证据降低讨论成本。

### 19.7 企业合规整改从恐慌到证据化推进

**用户张力**：公司收到客户或监管方的合规要求，内部不知道缺什么、谁负责、哪些风险必须先处理。

**系统工作方式**：

- `Probe` 先区分这是安全合规、隐私合规、流程合规、合同合规还是审计材料缺失。
- `Promise` 承诺“把模糊合规恐慌变成可审计整改计划”；涉及法律结论时必须标记为需专业人士裁决。
- 大模型负责要求解读、差距分析、整改优先级；小模型负责条款抽取、证据归档、材料状态标注。
- `Trust Gradient` 规定对外承诺、合同解释、法律判断必须人工和专业顾问确认。

**可验证动作**：

- 从客户安全问卷中抽取所有必须回答的问题。
- 判断每项要求是否已有证据文件。
- 把证据归类为政策、流程、截图、日志、合同、培训记录。
- 检查某回答是否超出了现有证据支持。
- 生成缺口清单和责任人草案。

**输出产物**：

- `Compliance Gap Map`：要求、现状、证据、风险、责任。
- `Audit Evidence Trail`：每个回答引用哪份材料。
- `Remediation Promise`：整改周期、里程碑、人工批准点。
- `Professional Review Pack`：需要律师、安全专家或 DPO 裁决的问题。

**价值证明**：模型不能替代专业法律判断，但可以极大减少材料搬运、条款抽取、证据核对和状态追踪，把人类精力留给高风险决策。

### 19.8 制造质量事故根因分析和跨部门协同

**用户张力**：工厂出现批量质量问题，生产、采购、质检、供应商互相推责，老板需要快速止损又不能误判。

**系统工作方式**：

- `Probe` 显影张力：真正问题是缺少事实链，而不是缺少会议。
- `Second Body` 感官接入检测记录、批次、供应商、工艺变更、投诉、维修记录；免疫系统标记证据薄弱的结论。
- 大模型负责假设树、根因路径、反证设计；小模型负责记录抽取、批次关联、异常归类。
- `Lens` 提供批次镜头、证据镜头、假设镜头、决策镜头、供应商协作镜头。

**可验证动作**：

- 从质检日志抽取异常时间、批次、指标。
- 把客户投诉按故障现象聚类。
- 检查某根因假设是否覆盖所有异常批次。
- 找出异常开始前后的工艺或供应商变更。
- 生成需要人工现场确认的检查项。

**输出产物**：

- `Incident Timeline`：问题发生、发现、扩散和处理时间线。
- `Root Cause Hypothesis Map`：假设、证据、反证、置信度。
- `Containment Plan`：临时隔离、复检、客户沟通、供应商取证。
- `Mutation Proposal`：未来如何让系统提前发现同类疼痛信号。

**价值证明**：复杂事故需要多人、多资料、多假设并行。系统把体力劳动和证据组织自动化，让人类集中在现场判断、责任裁决和风险承担。

### 19.9 个人健康管理从焦虑记录到医生可用材料

**用户张力**：用户长期不舒服，但描述混乱，体检报告、症状、饮食、睡眠、运动记录散在多个地方，见医生时说不清。

**系统工作方式**：

- `Probe` 只做信息整理和就医准备，不做诊断结论。
- `Promise` 承诺“把混乱健康记录整理成医生可快速理解的材料，并提示需要专业医疗判断的问题”。
- 小模型负责症状时间线、报告指标抽取、生活记录整理；规则程序负责文件归档、时间排序；大模型负责生成就诊摘要和问题清单。
- `Trust Gradient` 明确所有诊断、用药、治疗建议必须由医生决定。

**可验证动作**：

- 从体检报告中抽取日期、指标、异常标记。
- 把症状记录按时间线排序。
- 检查就诊摘要是否区分事实、主观感受和推测。
- 生成需要问医生的问题清单。
- 标出记录缺失的时间段。

**输出产物**：

- `Doctor Brief`：症状、时间线、报告摘要、已尝试事项。
- `Evidence Pack`：原始报告、截图、记录来源。
- `Question List`：用户最需要医生回答的问题。
- `Boundary Notice`：系统不做诊断，不替代医生。

**价值证明**：这里价值不是医疗判断，而是体力劳动和表达短板桥接。用户不再在就诊时靠记忆临场组织信息。

### 19.10 成人学习者从“想变强”到可执行能力训练

**用户张力**：用户说“我想学 AI/设计/英语/编程，但总是坚持不下去”。真实问题可能是目标太大、反馈太慢、练习不可验证、精力不稳定。

**系统工作方式**：

- `Probe` 显影用户想成为谁：更强的工程师、设计师、表达者，还是能独立做产品的人。
- `Promise` 承诺“用 30 天训练一个可观察的小能力，而不是泛泛学习一门课”。
- 大模型负责能力拆解、练习设计、反馈标准；小模型批改小练习、记录错误模式、生成复习卡片。
- `Human Bandwidth` 根据用户当天精力调整训练量。

**可验证动作**：

- 判断用户答案是否满足 rubric。
- 把错误归类为概念、表达、步骤、注意力问题。
- 从 10 次练习中找出重复薄弱点。
- 生成下一次 15 分钟训练任务。
- 检查学习日志是否包含输入、输出、反馈、修正。

**输出产物**：

- `Capability Training Promise`：30 天训练目标、验收标准。
- `Practice Move Set`：每日可执行、可反馈的小练习。
- `Learning Pain Signals`：重复失败和逃避点。
- `Progress Lens`：用户看见自己哪里变强，而不是只看学习时长。

**价值证明**：系统不只是推荐课程，而是把“我想变强但说不清”转成训练协议，同时承接复习、记录、批改、提醒等体力劳动。

### 19.11 开源维护者处理 Issue、PR、发布和社区信任

**用户张力**：维护者被 Issue、PR、版本发布、用户催促和文档维护压垮，真正缺的是可信的维护肌肉和决策仪表。

**系统工作方式**：

- `Probe` 区分维护者痛点是响应速度、质量风险、破坏兼容、文档债，还是社区沟通压力。
- `Execution Muscle` 批量分类 Issue、复现 bug、整理 changelog 草稿、检查 PR 风险。
- 大模型负责优先级、架构影响、破坏性变更判断和维护策略；小模型负责标签、摘要、相似问题匹配。
- `Trust Gradient` 规定关闭 Issue、合并 PR、发布版本必须人工批准。

**可验证动作**：

- 判断 Issue 是否包含复现步骤。
- 查找相似历史 Issue。
- 从 PR diff 中抽取影响模块。
- 检查 changelog 是否覆盖所有用户可见变更。
- 标记可能破坏兼容的 API 修改。

**输出产物**：

- `Maintainer Cockpit`：待处理、阻塞、风险、可批处理任务。
- `Release Evidence Trail`：每个发布项对应的 PR、测试、文档。
- `Community Response Drafts`：礼貌、准确、边界清晰的回复草稿。
- `Sustainability Pain Signal`：维护者过载指标和自动化提案。

**价值证明**：单模型能写回复，但维护开源需要信任、证据、权限和持续体力劳动。系统让维护者保留判断权，同时减少事务性消耗。

### 19.12 家装或大型个人项目的多方协调

**用户张力**：用户要装修、搬家、办婚礼或组织大型活动，脑子里全是事项、报价、供应商、时间节点和风险，无法稳定推进。

**系统工作方式**：

- `Probe` 识别用户真正担心预算失控、供应商不靠谱、审美决策疲劳、遗漏事项，还是家人意见冲突。
- `Promise` 承诺“把一次复杂生活项目变成可追踪、可授权、可验收的推进系统”。
- 小模型整理报价、合同条款、时间表、物品清单；工具负责提醒、归档、对比；大模型负责取舍建议和风险分析。
- `Lens` 提供预算镜头、进度镜头、决策镜头、供应商镜头、证据镜头。

**可验证动作**：

- 从报价单中抽取项目、单价、数量、总价、备注。
- 对比两个供应商报价差异。
- 检查合同中是否包含交付时间、验收标准、违约处理。
- 生成下周必须确认的事项。
- 标出预算超支风险。

**输出产物**：

- `Life Project Promise`：目标、预算、边界、决策权。
- `Vendor Evidence Pack`：报价、沟通记录、合同、风险。
- `Decision Batch`：集中让用户裁决的审美和预算问题。
- `Execution Muscle`：提醒、整理、追踪、核对。

**价值证明**：这证明系统不只服务代码和知识工作，也能承接生活中的高摩擦体力协调，释放用户精力。

### 19.13 志愿者救援或公益项目的信息调度

**用户张力**：公益组织临时面对大量求助、资源、志愿者、地点、优先级和风险，人工表格很快失控。

**系统工作方式**：

- `Probe` 明确目标不是“自动决策救援”，而是让人类协调者看清事实、优先级和资源缺口。
- `Second Body` 感官收集求助信息、资源位置、志愿者能力和状态；免疫系统标记不可信或重复信息。
- 大模型负责优先级解释、资源匹配策略和风险提示；小模型负责信息抽取、去重、地理/时间标签。
- 高风险调度必须由人类负责人确认。

**可验证动作**：

- 从求助消息中抽取地点、人数、紧急程度、联系方式。
- 检测重复求助。
- 判断资源需求类型：食物、药品、交通、住宿、医疗。
- 标记缺少关键字段的信息。
- 生成待确认清单。

**输出产物**：

- `Relief Coordination Lens`：需求、资源、志愿者、风险、未确认信息。
- `Evidence Trail`：每条信息来源、时间、确认状态。
- `Dispatch Drafts`：待人类批准的资源匹配建议。
- `After Action Memory`：重复阻塞、误报模式、下次改进。

**价值证明**：在高压场景中，系统价值不是替人做道德裁决，而是快速承接信息体力劳动，让负责人保持清醒。

### 19.14 企业数据分析从“看报表”到决策实验

**用户张力**：管理者有很多报表，但不知道到底该涨价、砍功能、投广告、改渠道，还是先修留存。

**系统工作方式**：

- `Probe` 追问管理者真正的不确定性：增长、利润、留存、渠道、产品价值还是团队执行。
- `Possibility Map` 生成多个可验证商业实验，而不是直接给结论。
- 小模型和规则程序处理数据清洗、指标计算、异常点标注；大模型负责解释、反方假设和实验设计。
- `Evidence Lens` 区分数据事实、推测和价值判断。

**可验证动作**：

- 检查数据字段缺失率。
- 计算每个渠道的转化漏斗。
- 标出异常时间段。
- 判断某结论是否被数据支持。
- 生成 A/B 实验的最小样本和风险提示。

**输出产物**：

- `Business Tension Map`：真正要解决的是增长、利润还是留存。
- `Experiment Portfolio`：低成本实验、预期指标、停止条件。
- `Decision Memo`：事实、推测、风险、建议。
- `Metric Pain Signals`：重复异常和数据质量问题。

**价值证明**：报表工具给数据，模型给解释；本系统把二者变成可执行实验和可审计决策。

### 19.15 产品经理做用户研究和路线图裁决

**用户张力**：产品经理被老板、销售、用户、研发同时拉扯，需求很多但不知道哪些是真问题。

**系统工作方式**：

- `Probe` 分析每个需求背后的张力：用户痛点、销售压力、老板愿景、技术债、竞争威胁。
- `Possibility Map` 给出不做、延后、实验、MVP、完整功能、流程改造等选项。
- 大模型负责需求归因、机会判断、路线图冲突分析；小模型负责访谈摘要、需求聚类、证据标注。
- `Lens` 给出用户证据、商业价值、技术风险、决策等待项。

**可验证动作**：

- 从访谈中抽取用户原话和具体场景。
- 判断需求是否有明确用户行为证据。
- 聚类相似需求。
- 检查 PRD 是否包含目标、非目标、验收、风险。
- 标记路线图冲突。

**输出产物**：

- `Requirement Evidence Map`：每个需求的证据强度。
- `Roadmap Decision Pack`：选项、代价、风险、反方。
- `Promise`：帮助产品经理减少伪需求，稳定推进高价值方向。
- `Stakeholder Briefs`：给老板、销售、研发不同镜头的说明。

**价值证明**：系统不是替产品经理拍板，而是把杂乱压力转成证据化选择，让产品经理的判断长板更长。

### 19.16 多个超级个体协作制作纪录片或课程

**用户张力**：导演、研究员、剪辑、设计、发行、讲师各自很强，但协作成本高，素材、审美、事实、版本和决策经常冲突。

**系统工作方式**：

- `Federation` 让每个超级个体声明能力、边界、可交付物和证据要求。
- `Promise` 定义共同承诺：在 8 周内交付一部 30 分钟纪录片或一套课程。
- 大模型负责整体叙事、冲突整合和质量评审；小模型处理素材标注、字幕、时间码、引用核验。
- `Lens` 展示叙事线、素材证据、制作进度、审美分歧、发行计划。

**可验证动作**：

- 给视频素材打人物、地点、主题、情绪标签。
- 检查旁白中的事实是否有来源。
- 把采访转写按主题聚类。
- 标记剪辑版本之间的差异。
- 生成发行素材清单。

**输出产物**：

- `Federated Production Contract`：各超级个体职责、边界、交付标准。
- `Narrative Evidence Trail`：每个叙事判断背后的素材。
- `Review Lens`：导演、研究、剪辑、发行各看不同状态。
- `Release Pack`：成片、字幕、文案、海报、发布计划。

**价值证明**：一群强个体协作时，难点不是谁更聪明，而是接口、证据、版本、边界和合并。系统证明“超级个体级联”不是口号。

### 19.17 企业安全事件响应和事后加固

**用户张力**：团队发现异常登录或数据泄漏迹象，既怕扩大事故，也怕误报影响业务。

**系统工作方式**：

- `Probe` 明确目标是防御性分析、事实整理和响应协同，不提供攻击指导。
- `Second Body` 感官收集日志、告警、资产、权限变更；免疫系统标记可疑路径和证据缺口。
- 大模型负责事件假设、影响面推断、响应顺序；小模型负责日志摘要、IOC 初筛、重复告警聚类。
- `Trust Gradient` 规定隔离账号、封禁 IP、通知客户等动作必须人工批准。

**可验证动作**：

- 从登录日志中抽取异常地理位置和时间。
- 聚合同一账号的失败登录。
- 检查某告警是否有相关资产变更。
- 生成待确认事实清单。
- 标记响应动作的业务影响。

**输出产物**：

- `Incident Evidence Trail`：时间线、资产、账号、告警、证据强度。
- `Containment Options`：隔离、监控、回滚、通知的代价。
- `Postmortem Draft`：事实、影响、根因、修复、未决。
- `Mutation Proposal`：新增检测规则、权限策略、演练计划。

**价值证明**：安全响应需要快速承接大量日志体力劳动，同时保留人类授权和责任边界。系统能显著降低混乱，但不越权执行高风险动作。

### 19.18 家庭或个人财务整理与风险可视化

**用户张力**：用户有多张银行卡、信用卡、贷款、保险、订阅、投资记录，但不知道现金流和风险在哪里。

**系统工作方式**：

- `Probe` 识别用户真正关心的是预算失控、债务压力、订阅浪费、保险缺口，还是投资决策焦虑。
- 系统只做整理、分类、风险提示和问题清单，不替用户做投资或法律税务决定。
- 小模型负责交易分类、订阅识别、文件归档；规则程序计算现金流、到期时间、重复扣款。
- 大模型负责解释结构、生成可问专业人士的问题。

**可验证动作**：

- 将交易记录归类为固定支出、可变支出、债务、收入、订阅。
- 找出重复扣款和异常金额。
- 生成未来 30 天现金流预测。
- 检查保险文件是否缺少保额、期限、免赔说明。
- 标记需要专业财务顾问确认的问题。

**输出产物**：

- `Personal Finance Lens`：现金流、债务、订阅、保险、待确认风险。
- `Document Evidence Pack`：账单、合同、保单、来源。
- `Decision Batch`：取消订阅、调整预算、咨询专业人士的问题。
- `Boundary Notice`：不提供投资建议，不替代专业服务。

**价值证明**：系统承接整理、归类、核对、提醒等体力劳动，让用户从财务焦虑进入可见状态，而不是陷入建议噪声。

### 19.19 招聘与团队组建从简历海洋到能力匹配

**用户张力**：创始人或负责人要招人，但简历很多、岗位不清、面试标准不稳定，担心招错人。

**系统工作方式**：

- `Probe` 先澄清团队真正缺的是执行力、架构能力、产品判断、沟通能力，还是补位某个短板。
- `Promise` 承诺“建立一个可证据化的人才筛选和面试系统”，不是替人自动录用。
- 小模型抽取简历事实、项目经历、技能关键词；大模型设计面试题、风险点、能力假设；人类做最终判断。
- `Lens` 展示候选人证据、岗位能力模型、面试反馈、风险和不确定性。

**可验证动作**：

- 从简历中抽取项目、职责、成果、技术栈。
- 检查候选人描述是否包含可验证结果。
- 把面试记录按能力维度标注。
- 生成追问问题。
- 检查评价是否混合了事实和主观印象。

**输出产物**：

- `Role Promise`：这个岗位承诺补强团队哪种能力。
- `Candidate Evidence Matrix`：候选人与能力维度的证据对应。
- `Interview Move Set`：每轮面试验证什么假设。
- `Hiring Decision Memo`：支持、反对、不确定、下一步。

**价值证明**：系统不是替人决定谁好，而是减少筛简历、整理反馈、对齐标准的体力劳动，让负责人把精力放在组织判断。

### 19.20 跨组织研究联盟攻关复杂问题

**用户张力**：多个团队想共同研究一个复杂议题，例如城市韧性、AI 安全、教育公平、供应链风险。每个团队都有能力，但资料、标准、方法、产物和责任难以对齐。

**系统工作方式**：

- `Federation` 让各团队声明能力、数据边界、隐私限制、可共享产物和证据标准。
- `Promise` 定义联盟级承诺：在限定周期内产出一份可被政策、产品或行动使用的研究成果。
- 大模型负责总问题框架、跨团队假设整合、冲突调解；小模型负责文献、数据、访谈、案例的标准化处理。
- `Lens` 分别展示总览、证据、团队贡献、冲突、隐私边界、政策建议和未决问题。

**可验证动作**：

- 将不同团队提交的材料映射到统一 schema。
- 检查某结论是否跨来源支持。
- 标记数据不能共享但可以共享摘要的部分。
- 聚类不同团队的冲突观点。
- 生成每周联盟进展简报。

**输出产物**：

- `Federated Research Contract`：能力、边界、贡献、证据标准。
- `Shared Evidence Graph`：跨团队证据网络。
- `Conflict Register`：分歧、原因、待验证动作。
- `Policy / Product Action Pack`：可执行建议、证据强度、风险。

**价值证明**：这是超级个体级联的高阶形态。一个强模型或一个强人类都无法单独完成跨组织协作；价值来自协议、证据、边界、联邦和可复用能力有机体。

## 20. 从案例反推的可行性判断

以上 20 个例子共同说明，本脑暴不是单纯愿景，而是有可落地结构：

| 被证明的点 | 案例中的体现 |
|---|---|
| `Probe` 有必要 | 用户通常一开始说不清任务，只能表达焦虑、野心、厌烦或失控感。 |
| `Promise` 比工作流更稳 | 复杂场景里用户关心的是系统承诺帮他推进哪种能力，而不是先画哪张流程图。 |
| `Second Body` 具象有效 | 感官、肌肉、免疫、记忆、睡眠、疼痛能覆盖发现、执行、防错、沉淀和改进。 |
| `Execution Muscle` 是刚需 | 大量价值来自承接资料整理、状态追踪、格式转换、核对、归档、提醒等体力劳动。 |
| `Verifiable Move` 是协作接口 | 小模型、工具、规则程序能可靠执行的前提是输入小、输出小、可检查。 |
| `Lens` 是 UI 核心 | 不同场景需要切换张力、证据、风险、进展、决策、疼痛和联邦视角。 |
| `Federation` 有长期价值 | 多个超级个体协作时，真正难点是能力声明、边界、证据、冲突和成果合并。 |

因此，下一阶段不应先做完整产品，而应选 2 到 3 个高价值场景做协议切片：

1. 一个偏知识生产：如研究论文、产品验证或内容创作。
2. 一个偏工程执行：如老旧代码库恢复或安全事件响应。
3. 一个偏生活/运营体力劳动：如电商运营、家装项目或个人财务整理。

每个切片只验证最小闭环：

```text
Tension Field
  -> Probe
  -> Promise
  -> Possibility Map
  -> Verifiable Move Set
  -> Execution Muscle
  -> Lens
  -> Evidence Trail
  -> Mutation Proposal
```
