# 项目总纲：核心目的

> 状态：当前总纲。
> 作用：约束 金箍 的架构、代码、测试、评审和迁移方向。
> 原则：任何新概念、新模块、新流程若不能服务本总纲，默认不应进入核心架构。

## 1. 一句话

金箍 的核心目的不是制造一个更会顺从的 代理，也不是把专家已经会做的事自动化，而是构建一个能力补全型 人工智能支架：让只有粗糙愿望、缺少专业能力的人，也能在 人工智能、工具、证据、验收和人类裁决的共同作用下，把想法推进为可检查、可迭代、可交付的现实成果。

更短地说：

> 金箍 要让普通人越过自身能力短板，把“我想要但我不会做”变成“我能判断、能推进、能交付”。

## 2. 根本服务对象

金箍 首先服务的不是已经能清晰拆任务、写 提示词、写 法、定标准、审结果的专家用户。

金箍 的根本服务对象是：

- 只有愿望但不知道该怎么表达的人。
- 有想法但缺少领域知识、方法论、审美、工程能力或验收标准的人。
- 能做最终价值判断，但不能独自完成专业路径设计的人。
- 不应被 人工智能 替代判断权，却需要 人工智能 扩展行动能力的人。

专家用户也应该受益，但专家效率提升不是最高目标。最高目标是能力补全。

## 3. 核心问题

传统 代理 / 流程编排 / 记忆 系统容易默认用户已经知道：

- 目标应该怎样定义。
- 任务应该怎样拆分。
- 需要哪些知识和材料。
- 什么方法是可行的。
- 什么结果算好。
- 什么风险必须避免。
- 哪些节点需要人类裁决。

这会导致系统天然偏向强用户：越懂的人越能驱动 人工智能，越不懂的人越只能得到表面回答。

金箍 要解决的核心问题是：

> 当人只给出不完整的愿望时，系统如何发现缺失能力，补齐必要知识、方法、标准、流程和执行力量，并把真正需要人判断的部分呈现给人？

## 4. 能力补全闭环

金箍 的基本闭环不是“用户下令 -> 代理 执行 -> 输出答案”，而是：

```纯文本
愿望进入
  -> 保存为可引用材料
  -> 诊断能力缺口
  -> 获取或生成必要知识
  -> 合成临时能力包
  -> 形成可执行工作契约
  -> 召集行者执行
  -> 产生候选成果
  -> 用证据和验收标准检验
  -> 把关键裁决点交还给人
  -> 沉淀为新的材料、方法和经验
```

这个闭环允许 代理、流程编排、工具、脚本、模型和人类专家参与，但它们都不是根目的。它们只是能力补全闭环中的行者或方法。

## 5. 架构必须长出的能力

金箍 的核心架构至少要长出以下能力，而不是仅靠提示词约束：

| 能力 | 说明 |
|---|---|
| 愿望保真 | 保存人的原始表达、偏好、犹豫和价值判断，不让 人工智能 猜测覆盖源头 |
| 缺口诊断 | 判断完成目标缺哪些知识、标准、方法、材料、工具和角色 |
| 材料获取 | 在需要时主动收集事实、案例、约束和背景，并保留来源与可信度 |
| 能力合成 | 为当前目标生成可执行的临时 法、方法、检查表或流程，而不是要求用户预先会写 |
| 工作契约 | 把模糊愿望转为可执行、可验收、可拒收、可复盘的工作单元 |
| 行者约束 | 使用 代理 的生成力和工具力，但不让 代理 独占状态、目标、记忆、验收和责任 |
| 验收生成 | 在用户不会定标准时，帮助生成可解释的候选标准，并允许人类修正 |
| 证据闭环 | 重要结论、成果和状态变化必须携带证据、理由、来源或测试结果 |
| 裁决减负 | 不把所有细节都推给人，只把价值取舍、风险授权和无法替代的判断呈现给人 |
| 经验沉淀 | 将有效材料、方法、标准和失败教训沉淀为后续可复用能力，而不是污染长期记忆 |

## 6. 与 代理 和 流程编排 的关系

金箍 不以“不同于 代理”为目的。为了故意不同而不同没有价值。

金箍 应该兼容 代理 和 流程编排 的优点：

- 代理 适合开放推理、生成候选路径、调用工具、处理模糊问题。
- 流程编排 适合稳定流程、可重复执行、权限边界、恢复和观测。

但 金箍 不能退化为 代理 外面套一层日志，也不能退化为更复杂的 流程编排 画布。

本项目判断一个设计是否成立时，不问“它是不是看起来更像相业”，而问：

> 它是否比普通 代理 / 流程编排 更能帮助低能力起点的人完成高能力要求的目标？

若答案是否定的，该设计就应被修改、降级或删除。

## 7. 人的不可替代位置

金箍 不是让 人工智能 替人决定人生目标、审美、价值、责任和风险承受。

人的位置是：

- 发愿：提出愿望、偏好、问题、痛点和价值方向。
- 授权：决定哪些成本、权限、风险和外部影响可以被允许。
- 裁决：在多个合理方向之间做价值选择。
- 负责：对最终采用的结果承担人类责任。

人工智能 可以建议、模拟、反驳、补全、执行、评审和解释；但不能把人的价值源头改写成自己的目标。

## 8. 对相业架构的约束

相业术语只有在服务总纲时才有意义。

- `相` 的价值不是“记录更多东西”，而是让愿望、材料、证据、标准、过程和成果可引用、可迁移、可复盘。
- `业` 的价值不是“包装任务”，而是把模糊变化变成可执行、可验收、可拒收的工作契约。
- `行者` 的价值不是“换名 代理”，而是在明确位置、方法、边界和验收下承接工作。
- `律` 的价值不是“限制 人工智能 发挥”，而是把风险、权限、成本和质量边界变成可执行约束。
- `证` 的价值不是“多写解释”，而是让成果可信、可检查、可追责。
- `藏` 的价值不是“长期记忆越多越好”，而是沉淀经验证明有效、可复用、低污染的能力。

如果某个术语不能在实现中证明上述价值，应先降级为讨论概念，不进入核心协议。

## 9. 代表性验收场景

本总纲的代表性验收场景：

> 一个完全不懂写作的孩子，只给出一句话：“如果某个平行宇宙中人类是蛋生的会怎样？”金箍 应帮助他补齐必要知识、生成写作方法和验收标准、设计执行路径、产出候选小说，并把他真正能判断的选择交还给他，而不是要求他先成为网文专家。

这个场景不是唯一产品方向，但它暴露了 金箍 必须解决的核心矛盾：

- 用户没有能力定义专业路径。
- 人工智能 有能力生成路径，但容易自说自话。
- 系统必须补齐能力，同时保护人的愿望、判断权和可理解性。

## 10. 设计红线

以下情况视为偏离总纲：

- 只让强用户更强，却没有降低弱用户的能力门槛。
- 要求用户先写好 法、标准、流程，系统才会工作。
- 把聊天上下文当唯一真相源。
- 让 代理 同时决定目标、记忆、拆分、执行、验收和完成声明。
- 用大量日志替代可用状态、证据和裁决界面。
- 把所有不确定问题都推给人类，制造决策地狱。
- 为术语完整性保留概念，而不是为能力补全保留概念。

## 11. 当前开放问题

以下问题尚未定论，后续架构和实验必须继续回答：

- 能力缺口如何被可靠诊断，而不是由 人工智能 任意脑补？
- 临时能力包如何生成、测试、复用和废弃？
- 验收标准如何在用户不懂领域时生成，同时不冒充客观真理？
- 哪些裁决必须交给人，哪些可以由程序硬规则或 人工智能 评审完成？
- 如何避免相、证、日志和藏膨胀为上下文地狱？
- 如何证明 金箍 相比普通 代理 / 流程编排 在低能力起点场景中有架构性优势？

这些问题不是总纲的反例，而是后续实现必须用实验回答的核心工作。
