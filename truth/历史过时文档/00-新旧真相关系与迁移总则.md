# 新旧真相关系与迁移总则

## 1. 为什么建立 `truth/`

当前项目原本以 `docs/` 为唯一文档系统，这适合维护既有 Cyber Editor 的产品、架构、测试和实现细节。

但后续重构目标已经不只是“把现有文档落地到代码”，而是重新思考一个更泛化的、文件原生的、意图驱动的 AI 能力框架。继续把这些想法塞进 `docs/` 会让旧产品真相和新范式真相互相污染。

因此建立与 `docs/` 平级的 `truth/`：

```text
truth/  新真相：未来方向、原则、对象模型、文件协议、重构依据
docs/   旧真相：既有 Cyber Editor 的需求、设计、架构、测试、历史细节
```

## 2. 优先级

从本文件创建后，后续讨论未来重构时默认优先级为：

1. 用户当前明确指令。
2. `truth/` 中标记为“当前真相”的新方向、新原则、新对象模型。
3. `docs/` 中可复用的旧系统细节。
4. 当前 `src/` 代码事实。
5. 历史临时报告和旧状态标签。

截至第三阶段，`03-超级个体外骨骼与能力集群真相.md` 是当前综合真相；`04-能力包协议与可验证动作原子化.md` 是当前底层协议草案；`05-身体内核与能力包软件架构方案.md` 是当前软件架构方案；`01-从0开始的未来愿景脑暴.md` 与 `02-Codex的第二视角脑暴.md` 保留为历史脑暴素材和概念来源，不再作为直接决策真相源。后续若重新启用 `01` 或 `02` 的概念，应先吸收到当前真相文档或新的当前真相文档。

如果 `truth/` 与 `docs/` 冲突：

- 不要自动调和。
- 不要把旧文档当成更高权威。
- 应明确标注：`truth/` 是新目标，`docs/` 是旧状态或迁移素材。

## 3. `truth/` 负责什么

`truth/` 负责：

- 未来系统的北极星。
- 人类意图识别的原则。
- 可组织智能的对象模型。
- 文件原生协议。
- 记忆、技能、能力、原子工作、运行证据等新概念的边界。
- 新系统如何从旧代码迁移。
- 哪些旧概念应该淘汰、保留、降级或重命名。

`truth/` 暂时不负责：

- 证明当前代码已经实现。
- 维护旧 UI 的完成状态。
- 替代测试证据。
- 承诺某个功能已可用。

## 4. `docs/` 的保留价值

`docs/` 不立刻删除。它保留以下价值：

- 当前应用的真实产品细节。
- 已有页面、服务、IPC、测试和证据矩阵。
- 旧架构的边界和技术债。
- 可迁移的详细设计素材。
- 当前代码对照索引。

但 `docs/` 将逐步降级为：

```text
legacy reference / migration source / implementation evidence
```

而不是未来重构的思想源头。

## 5. 迁移方式

后续迁移应遵循：

1. 先在 `truth/` 形成新原则。
2. 再从 `docs/` 抽取可复用素材。
3. 对每个旧对象标注命运：
   - keep：保留。
   - rename：重命名。
   - split：拆分。
   - merge：合并。
   - demote：降级为实现细节。
   - remove：淘汰。
4. 最后才修改代码。

禁止直接把 `docs/` 整体搬进 `truth/`。`truth/` 不是归档目录，而是新系统的生成空间。
