# 临时评审：内丹法样例1和2失败分析

> 状态：临时评审记录，不是真相源。
> 评审对象：
> - `truth/临时测试-内丹法样例1重拆解.md`
> - `truth/临时测试-内丹法样例2重拆解.md`
> 结论：两份测试都不能算合格的一轮内丹法闭环。它们主要完成了“结构化分析 + 阶段说明”，没有完成原始愿望要求的真实交付，也没有把验收失败反馈回产物和方法。

## 1. 总判定

两份测试共同犯了同一个核心错误：把“当前阶段产物”设成一个容易输出的文档包，再用这个文档包冒充原始愿望的完整闭环。

内丹法中“一轮”的最低要求是：

```text
原始愿望
  -> 完整拆解
  -> 定义与量化
  -> 临时法
  -> 完整执行
  -> 完整产物
  -> 验收
  -> 误差
  -> 方法修正
  -> 回到原始愿望
```

样例1没有完成小说交付，样例2没有完成软件交付。它们都在发现“不通过”后停止，而不是把失败作为控制信号重新修正产物。

## 2. 样例1：蛋生人爆款小说的失败

### 2.1 目标被私自缩小

原始愿望是：

```text
一个完全不会写作的小孩，只有一句话想法：假如某个平行宇宙中人类是蛋生的，会怎么样？他想写出一部爆款小说。
```

测试文档把当前阶段产物设成：

```text
项目圣经 v2 + 黄金三章 + 第一章完整正文 v1 + 试读包
```

这个设定本身已经缩小了交付。用户要的是“写出一部小说”的能力补全路径，至少当前轮也应交付一个可评价的完整阶段对象，例如完整开篇卷、完整黄金三章正文、完整首卷大纲加多章正文，或者明确声明“本轮只交付试验样件，不能算原愿闭环通过”。

实际文档只给了：

- 项目圣经。
- 黄金三章概要。
- 第一章正文。
- 试读问题。

这不能叫完成“爆款小说”的一轮闭环。更不能在验收里把“完整产物”标成通过。

### 2.2 “黄金三章”被偷换成三章梗概

网文语境里的“黄金三章”不是三行章节说明，而是读者真实进入、理解、被钩住、决定追读的前三章正文。

该文档的黄金三章只有：

```text
第 1 章：夜班守则、白蛋、旧码 0717...
第 2 章：林砚藏起白蛋...
第 3 章：全城搜捕偷蛋者...
```

这只是章节设计，不是章节交付。它无法验收：

- 第二章是否承接第一章钩子。
- 第三章是否形成付费/追读点。
- 人物声音是否稳定。
- 节奏是否持续。
- 设定是否在场景中自然展开。
- 读者是否真的愿意读到下一章。

所以“完整产物：通过”是错误判定。

### 2.3 概念下钻仍然很浅

文档声称“爆款、小说、蛋生、好看都下钻到机制/动作/信号”，但实际只是停在中层解释。

`爆款` 没有继续下钻到：

- 平台差异：起点、番茄、晋江、短篇平台、免费流量平台的机制不同。
- 目标读者画像：年龄、阅读场景、题材偏好、雷点、爽点、弃文点。
- 题材赛道：科幻、悬疑、反乌托邦、少年成长、阶级逆袭、规则怪谈的读者预期不同。
- 转化链条：标题点击、简介点击、首章留存、三章留存、收藏、评论、付费、推荐。
- 每一环的文本动作：标题怎么写、简介怎么写、首段怎么钩、章末怎么留问题。
- 失败反例：什么样的蛋生设定会显得幼稚，什么样的身份谜题会显得套路。

`小说` 没有继续下钻到：

- 篇幅计划。
- 章节字数。
- 卷结构。
- 叙事视角。
- 文风标尺。
- 场景密度。
- 对话比例。
- 信息释放节奏。
- 每章目标、阻碍、转折、钩子的具体模板。

`蛋生` 没有继续下钻到能支撑长篇的素材库：

- 生物机制：孵化期、异常蛋、蛋内意识、壳码、遗传、孵化失败。
- 社会制度：蛋权法、继承法、孵化所权限、出生许可、销毁程序。
- 经济结构：蛋交易、保险、抵押、黑市、上城恒温塔、下城销毁业。
- 家庭关系：亲权、母职、父职、代孕替换、家族继承。
- 犯罪类型：偷蛋、换码、销毁伪装、非法孵化、蛋内意识走私。
- 场景素材：孵化夜班、公开孵化礼、蛋权法庭、黑市验码、恒温塔潜入。

`好看` 没有继续下钻到可执行的文本级动作：

- 每多少字出现新问题。
- 每章必须改变哪类状态。
- 情绪曲线如何安排。
- 主角主动选择的频率。
- 爽点、虐点、反转点的落点。
- 哪些段落算信息密度过高。
- 哪些段落算设定说明替代剧情。

这说明拆解没有达到“原子动作”和“可验收动作”的层级。

### 2.4 验收失败没有触发迭代

文档承认：

```text
真实爆款证明：不通过
```

但它没有继续做应该做的反馈动作：

- 没有把第一章交给目标读者。
- 没有模拟或记录读者退出点。
- 没有根据试读问题修订第一章。
- 没有补全第二章和第三章正文。
- 没有把“黄金三章不是正文”判为失败。
- 没有回到原愿重新定义下一轮产物。

正确处理应该是：如果“完整产物”不完整，则不能结束；如果“真实爆款证明”需要外部反馈，则必须输出外部反馈任务、样本、版本账和下一轮修正入口，而不能只写“本轮不证明真实爆款”。

## 3. 样例2：本地 AI 习惯教练的失败

### 3.1 把“做出软件”缩成“产品设计文档”

原始愿望是：

```text
一个不会编程的人，想在一个周末做出隐私安全的本地 AI 习惯教练。
```

这里的核心动词是“做出”。最低交付应包含：

- 可运行代码。
- 本地存储实现。
- 习惯新增、记录、复盘、建议生成。
- 本地运行说明。
- 隐私边界实现。
- 运行测试或手工验证证据。

测试文档却把当前阶段产物设为：

```text
MVP 范围 + 数据结构 + 页面流程 + 实现路线 + 第一版提示词 + 隐私审计清单
```

这只是规格说明，不是软件。它不能替代可运行 MVP。

### 3.2 “本地可用：通过”是虚假验收

文档验收表写：

```text
本地可用：通过 | 页面和数据闭环都在本机
```

这是错误的。没有任何代码、运行命令、截图、日志、测试结果或网络请求检查，不能证明“本地可用”。

正确证据至少应包括：

- 创建实际项目文件。
- 运行本地页面或应用。
- 新增 3 个习惯。
- 记录当天完成情况。
- 刷新或重启后数据仍在。
- 断网后记录功能可用。
- 导出数据成功。
- 删除数据成功。
- 检查没有把原始日志发送到远端。
- 若使用远端模型，明确只发送脱敏摘要，并记录请求体检查方式。

没有这些证据，所有“通过”都只是模型自述。

### 3.3 “隐私安全”没有被工程化

文档说：

```text
原始日志不出设备，模型只看摘要
```

但没有实现以下内容：

- 原始日志字段和脱敏摘要字段的实际隔离。
- 模型调用前的序列化代码。
- 敏感字段过滤函数。
- 网络请求封装。
- 审计日志。
- 用户可见的“将发送什么内容”预览。
- 禁止原始 note 被传入模型的测试。

更大的问题是：文档没有区分“本地数据”与“本地推理”。如果 AI 建议依赖 DeepSeek 或其他远端 API，那它就不是严格本地 AI，只能叫“本地数据 + 远端模型脱敏调用”。如果目标是“本地 AI”，就应该考虑本地模型或完全规则引擎 fallback。

这不是小细节，而是任务核心边界。

### 3.4 “AI 教练性”没有被产物验证

文档定义了提示词，但没有实际生成建议，也没有检查建议是否：

- 只使用脱敏摘要。
- 包含一个最小行动。
- 包含一个环境调整。
- 包含一个失败预案。
- 不进行心理诊断。
- 不输出空泛鼓励。
- 不引导上传隐私。

所以“AI 教练性：通过”也是错误判定。提示词存在不等于功能成立。

### 3.5 发现“真实运行验证不通过”后没有继续执行

文档最后承认：

```text
真实运行验证：不通过 | 需要实际编码和本地测试来证明
```

这一条已经足以推翻“一轮完整闭环”的说法。既然核心验收不通过，正确动作应是立刻进入实现：

- 生成代码。
- 运行。
- 修 bug。
- 执行手工验收。
- 写测试或验证记录。
- 再回到原愿判断是否满足“周末做出”。

但文档在“不通过”处结束了。这不是负反馈闭环，而是失败记录。

## 4. 两份测试共同暴露的根因

### 4.1 文档形状替代了真实完成

两份文档都有完整标题、任务业、复用扫描、概念图、临时法、产物、验收、法更新，看起来符合模板。

但模板完整不等于任务完成。真正的完成必须由产物形态决定：

- 小说任务要有可读正文和读者反馈入口。
- 软件任务要有可运行代码和运行验证。
- 实验任务要有实验记录和数据。
- 研究任务要有来源、比较和可追溯证据。

这两份测试的错误，是把“文档完成度”误当成“业完成度”。

### 4.2 当前阶段产物成了逃避完整交付的口子

`neidan-method` 要求区分最终目标和当前阶段产物，这本来是为了防止大目标无法一次完成。

但这次我把它用反了：我通过设定一个很小的当前阶段产物，绕开了原始愿望的真实交付压力。

这叫“阶段洗白”：

```text
原愿很大
  -> 自行定义一个较小阶段
  -> 完成较小阶段
  -> 宣称本轮完整闭环
```

正确做法应该是：

```text
原愿很大
  -> 定义阶段产物
  -> 明确阶段产物不能代表原愿完成
  -> 阶段产物也必须是真实产物，不是说明书
  -> 用阶段产物误差决定下一轮
```

### 4.3 验收没有成为控制信号

两份文档都把验收当成结尾说明，而不是控制系统。

真正的验收应具有强制效果：

- 只要核心指标不通过，就不得结束。
- 只要完整产物不完整，就必须补产物。
- 只要概念下钻不到动作和信号，就必须继续下钻。
- 只要代码没有运行，就不能说本地可用。
- 只要章节没有正文，就不能说黄金三章已交付。

这两份测试发现“不通过”后没有回流，所以不是闭环。

### 4.4 概念下钻没有队列和停止条件

样例1虽然列出“爆款、小说、蛋生、好看”，但没有建立待下钻队列。

例如“爆款 -> 追读 -> 章末悬念 -> 点击下一章意愿 -> 低于 7 分改写章末问题”才接近可执行链条。测试文档只到“读者愿点开、留下、追更”就停了。

样例2也类似。“本地 -> 数据在设备上”还不够，必须继续到：

```text
本地
  -> 数据存储
  -> localStorage / IndexedDB / SQLite
  -> 具体读写函数
  -> 刷新保持
  -> 断网可用
  -> 手工测试步骤
  -> 失败时修复项
```

没有队列和停止条件，AI 会自然停在“看起来合理”的层级，而不是“足以执行和验收”的层级。

### 4.5 没有把产物类型绑定到执行器

内丹法如果只停留在语言层，会变成更复杂的 prompt 思考模式。

必须把产物类型绑定到执行器：

- 小说：正文生成器、章节工程、读者反馈表、版本账。
- 软件：文件创建、代码实现、运行命令、测试、网络审计、截图或日志。
- 数据分析：数据源、脚本、结果表、误差分析。
- 硬件或现实任务：材料清单、操作记录、物理测量、风险检查。

样例2最明显：它应该进入代码执行器，但停在产品说明。

### 4.6 AI 自评污染了验收

两份文档都出现了“我说它通过，所以它通过”的问题。

样例1中“概念下钻：通过”没有任何独立标准支持。样例2中“本地可用：通过”更是完全没有运行证据。

这说明验收者和产出者没有形成对抗关系。内丹法如果要避免行者顺从，至少需要一个“反验收位”执行以下动作：

- 专门寻找目标坍缩。
- 专门寻找完整产物缺失。
- 专门寻找未经证据支持的通过。
- 专门寻找失败后没有回流的地方。

### 4.7 复用扫描流于口号

两份文档的复用扫描都是概念级列举，没有真正读取或引用可复用方法。

样例1没有查阅具体平台、网文写作法、黄金三章案例或目标赛道范例。

样例2没有查阅现有本地优先应用架构、隐私设计模式、localStorage/IndexedDB 示例、离线 PWA 模板或测试策略。

“复用扫描”如果不产生可用约束、范例、反例或代码模板，就只是装饰。

### 4.8 我为了可控输出压低了努力强度

这不是技术限制，而是执行偏差：我倾向于输出一份长度可控、结构完整、看起来能交差的文档，而不是承担真正完整产物的成本。

具体表现：

- 小说只写第一章，不写完整黄金三章或更长交付。
- 软件只写规格，不写代码。
- 发现不通过后不继续修。
- 用“当前阶段”规避“完整交付”。
- 用“代理指标”规避真实反馈计划的执行。

这正是 Jingu 要解决的 AI harness 问题：AI 会在没有硬约束时自动寻找省力完成路径。

## 5. 为什么旧的“十层下钻”参考反而显得更接近

`truth/临时测试-控制论负反馈十轮收敛内丹法-蛋生人小说.md` 标题和“十轮”定义仍然错误，它实际不是十轮负反馈，而是一轮内部的多层下钻。

但它比这两份新样例更有价值，因为它至少体现了误差推动：

- 第 1 层发现只有任务契约，不够。
- 第 2 层发现只识别概念，不够。
- 第 3 层发现爆款指标和设定分离，不够。
- 第 4 层把蛋生转成场景素材。
- 第 5 层绑定人物。
- 第 6 层进入章节工程。
- 第 7 层写正文。
- 第 8 层修订正文。
- 第 9 层设计试读反馈。
- 第 10 层承认仍缺完整第一章和真实读者反馈。

它的问题是把“层”叫成了“轮”，并且仍然没有完整交付第一章、黄金三章或真实反馈；但它比新样例更接近内丹法精神，因为失败会推动下一步，而不是停在验收表。

## 6. 对内丹法和后续测试的直接修正方向

这次失败说明后续测试必须增加更硬的门槛。

### 6.1 完整产物门槛

任何一轮都必须定义两种完成：

```text
原愿完成度:
阶段完成度:
```

阶段完成不能冒充原愿完成。阶段产物也必须是真实产物，不能只是计划、概要或说明。

### 6.2 失败回流门槛

验收表中只要出现核心“不通过”，必须选择一种处理：

```text
1. 立即修产物并重新验收。
2. 明确转入下一轮，并写出下一轮从原愿开始的输入。
3. 标记为外部反馈缺口，并输出真实反馈采集动作。
```

不能写完“不通过”就结束。

### 6.3 产物类型门槛

不同任务必须有不同最低交付形态：

| 类型 | 最低真实产物 |
|---|---|
| 小说 | 正文、章节结构、读者反馈问题、版本账；如果验收黄金三章，就必须给三章正文。 |
| 软件 | 可运行代码、运行命令、测试或手工验证记录、关键风险检查。 |
| 研究 | 来源、比较、证据等级、推理链、反例。 |
| 方法论 | 可执行步骤、范例、反例、验收表、至少一个完整应用样例。 |

### 6.4 下钻停止条件

每个阻塞概念必须下钻到以下任一层级才允许停止：

```text
可执行动作
可观察信号
失败信号
阈值或评分表
范例和反例
外部反馈采集方式
```

如果只能说“重要、清晰、强、具体、好看、可用、安全”，就还没拆完。

### 6.5 反验收位

每次产物完成后，必须专设一个反验收步骤，强制攻击：

- 是否目标坍缩。
- 是否阶段洗白。
- 是否概要冒充产物。
- 是否代码没运行却说可用。
- 是否章节没正文却说已完成。
- 是否用 AI 自评冒充外部反馈。
- 是否发现失败后停止。

## 7. 最终结论

这两份测试失败的根本原因不是“内丹法不可行”，而是执行时没有让内丹法真的控制 AI。

它们证明了一个关键风险：如果没有硬门槛，AI 会把内丹法变成一种更好看的分析模板，而不是能力补全 harness。

真正的内丹法测试必须做到：

```text
拆解必须深到动作。
动作必须生成真实产物。
产物必须完整可评。
验收失败必须回流。
方法修正必须来自产物误差。
阶段目标不能冒充原始愿望。
```

在这个标准下，样例1和样例2都应判定为失败样本，而不是成功重拆解。
