# 能力包协议与可验证动作原子化

> 状态：当前底层协议草案。
>
> 本文档用于纠正 `03-超级个体外骨骼与能力集群真相.md` 中“案例过大、实现过浅”的问题。`03` 说明为什么要做第二身体与能力集群；本文说明这个“身体”如何装载、替换、组合、验证能力包。

## 0. 本次纠偏

`03` 里的 20 个复杂例子仍然偏应用层。它们能说明愿景价值，但不能说明系统怎么实现。

更准确的分层应该是：

```text
我们不直接做“创业助手、论文助手、电商助手、健康助手”。

我们做：
  一个能装载义体的身体框架
  + 一套能力包协议
  + 一套原子动作协议
  + 一套权限/证据/镜头/联邦协议

具体任务能力由可装配、可替换、可组合、可验证的能力包提供。
```

类比：

```text
用户 = 人类意志、品味、责任、授权
系统 = 赛博身体 / 神经底座 / 能力装载框架
能力包 = 可插拔义体
动作 = 神经脉冲级别的可验证最小动作
镜头 = 人类观察义体状态的感官界面
联邦 = 多个增强个体之间的接口
```

所以真正要先定义的不是“20 个应用”，而是：

- 能力包如何声明自己。
- 能力包能插到身体的哪个槽位。
- 能力包需要什么权限、资源、工具、模型和上下文。
- 能力包暴露哪些可验证动作。
- 动作如何小到可以被小模型、工具或规则程序可靠执行。
- 动作如何产出证据。
- 能力包如何被沙盒安装、评估、授权、升级、卸载。
- 多个能力包如何组合成应用层解决方案。

## 1. Frontier Refresh

日期：2026-05-10。

本协议草案参考以下稳定方向，而不是复制某个框架：

| 来源 | 对本文档的约束 |
|---|---|
| JSON Schema：`https://json-schema.org/docs` | 能力包、Move、Evidence、Lens 等对象应有明确 schema、`$schema`、版本和校验边界。 |
| OpenAPI Specification：`https://spec.openapis.org/oas/latest.html` | 外部工具/API 能力应有清晰输入输出、错误、认证、安全和兼容性描述。 |
| Semantic Versioning：`https://semver.org/` | 能力包和协议必须有版本语义，破坏性变更不能假装兼容。 |
| MCP Specification：`https://modelcontextprotocol.io/specification/2024-11-05/` | 外部工具、资源、提示、根目录等边界应协议化；host 应保持用户授权与控制。 |

提取出的工程要求：

- schema authority 不能只靠散文描述，必须有机器可校验 schema。
- 引用必须有解析规则，缺失目标必须有失败行为。
- 版本必须说明兼容、升级、降级和废弃策略。
- 能力包不能绕过 host 的权限、根目录、工具、网络和人类授权边界。

## 2. 正确分层

未来系统不应按“应用场景”分层，而应按“身体底座”和“义体能力”分层。

```text
Human
  意志 / 品味 / 价值判断 / 授权 / 否决

Body Kernel
  能力包装载、权限、运行、证据、镜头、记忆、联邦

Capability Package
  可插拔义体：声明能力、动作、镜头、权限、资源、测试

Capability Module
  能力包内部模块：感官、肌肉、认知辅助、免疫、记忆、联邦接口

Verifiable Move
  可验证最小动作：小输入、小输出、可检查、可重试、可归因

Executor
  大模型 / 中模型 / 小模型 / 工具 / 脚本 / 人类

Evidence
  每个动作产生的证据、状态、错误、产物和审计记录
```

应用层案例应该只是能力包组合后的结果。

例如“老旧代码库恢复”不应该是系统内置功能，而应由这些能力包组合：

```text
codebase-sense.cap
doc-code-diff.cap
test-runner.cap
risk-immune.cap
refactor-planner.cap
evidence-lens.cap
```

## 3. Body Kernel：我们真正要做的“人本身”

`Body Kernel` 是装载义体的身体，不是某个具体义体。

它至少包含 12 个内核服务：

| 内核服务 | 职责 | 不负责 |
|---|---|---|
| Package Loader | 安装、卸载、启用、禁用、升级能力包。 | 不内置具体业务逻辑。 |
| Schema Registry | 管理协议、包、Move、Evidence、Lens 的 schema。 | 不接受无 schema 的自由文本能力。 |
| Slot Registry | 定义身体槽位：感官、肌肉、免疫、记忆、镜头、联邦等。 | 不允许能力包随意声明未知能力面。 |
| Permission Kernel | 管理文件、网络、工具、执行、写入、外发、人类授权。 | 不让能力包直接越权。 |
| Context Mount | 把项目、文件、资源、记忆、外部数据挂载给能力包。 | 不把全部上下文一次性塞给模型。 |
| Move Runtime | 调度和运行可验证动作。 | 不执行无法验收的大块任务。 |
| Executor Router | 根据 Move 要求选择大模型、小模型、工具、脚本或人类。 | 不把所有任务都丢给最大模型。 |
| Evidence Store | 存储动作输入、输出、状态、错误、证据、产物引用。 | 不只保存聊天记录。 |
| Lens Renderer | 把能力包状态投影给人类。 | 不把 UI 当真相源。 |
| Trust Kernel | 管理能力包和动作的信任等级。 | 不默认新能力全自动。 |
| Mutation Gate | 接收能力改进提案、沙盒验证、人工批准。 | 不让系统私自进化。 |
| Federation Bus | 支持多个超级个体或能力包之间协作。 | 不默认共享私有记忆。 |

这才是本项目的主产品。

能力包只是装在身体上的义体。

## 4. 能力包槽位

能力包不能只是“一个 prompt 文件夹”。它必须声明自己插在哪些槽位。

| 槽位 | 类比 | 能力包能做什么 | 典型动作 |
|---|---|---|---|
| `sense` | 感官 | 观察环境、文件、状态、外部变化。 | scan、observe、detect、extract。 |
| `cognition` | 认知辅助 | 结构化、推理、规划、比较、生成候选。 | classify、draft、rank、plan。 |
| `muscle` | 肌肉 | 执行低风险、可验证、可回滚动作。 | rename、format、run、sync、archive。 |
| `immune` | 免疫 | 发现错误、越权、幻觉、质量下降。 | validate、red_team、risk_check。 |
| `memory` | 记忆 | 生成、压缩、遗忘、检索经验。 | summarize、index、compact、forget。 |
| `lens` | 镜头 | 呈现状态、证据、决策、风险。 | render_view、explain_state。 |
| `federation` | 联邦接口 | 暴露能力、接收协作、交换证据。 | publish_capability、request_help。 |
| `governance` | 治理 | 权限、审批、审计、升级、回滚。 | request_approval、audit、rollback。 |

能力包可以占多个槽位，但必须逐项声明。

例如：

```yaml
slots:
  - sense
  - muscle
  - lens
```

表示它能观察、执行和展示，但不允许它做记忆沉淀、联邦共享或权限治理。

## 5. 能力包文件结构

一个能力包应该是可复制、可版本控制、可审计的文件夹。

```text
capabilities/
  codebase-recovery/
    capability.yaml
    README.md
    schemas/
      inputs.schema.json
      outputs.schema.json
      evidence.schema.json
    moves/
      scan-entrypoints.move.yaml
      summarize-module.move.yaml
      detect-doc-code-drift.move.yaml
      locate-first-test-failure.move.yaml
    tools/
      tool-bindings.yaml
    lenses/
      risk-map.lens.yaml
      progress.lens.yaml
      evidence.lens.yaml
    permissions/
      requested.yaml
      approved.yaml
    tests/
      contract-tests.yaml
      golden/
        sample-project/
        expected-evidence.json
    examples/
      run-001/
        input.yaml
        evidence.json
        output.md
    migrations/
      1.1.0-to-1.2.0.yaml
    CHANGELOG.md
```

原则：

- `capability.yaml` 是包的入口和唯一 manifest。
- `moves/` 里的每个动作必须可单独校验。
- `schemas/` 必须覆盖输入、输出和证据。
- `permissions/approved.yaml` 不能由包自己写入，只能由 host 生成。
- `examples/` 不是宣传材料，而是可回放的验收样本。
- `migrations/` 描述版本升级行为。

## 7. Move 不是任务，是神经脉冲

`Verifiable Move` 必须比“任务”更小。

分层如下：

```text
Application Scenario
  例如：恢复老旧代码库

Capability Package
  例如：codebase-recovery

Capability Module
  例如：entrypoint-sensing

Operation
  例如：构建代码入口地图

Verifiable Move
  例如：扫描 workspace 中所有 IPC 入口

Step
  例如：运行 rg 查询、解析一行结果

Assertion
  例如：输出必须包含 file、line、symbol、direction
```

能被调度和审计的最小单位应该是 `Move`。

`Step` 太细，会把系统变成脚本解释器。

`Operation` 太粗，会让小模型和工具无法可靠验收。

## 8. Move 原子化判定

一个 Move 只有满足以下条件，才算足够原子。

| 判定项 | 合格标准 | 不合格示例 |
|---|---|---|
| 单一动词 | 只做 scan、extract、classify、validate、draft、run、write 中的一类。 | “分析代码库并提出重构计划”。 |
| 输入小 | 输入是一个文件、一个片段、一个列表或一个明确查询。 | “整个项目上下文”。 |
| 输出小 | 输出是结构化对象、有限列表、布尔判断或一个小产物。 | “完整方案”。 |
| 可验证 | 有 schema、规则、测试、人工抽样或外部证据。 | “看起来不错”。 |
| 可重试 | 失败后可以单独重试，不必重跑整个任务。 | “重新做整个项目”。 |
| 副作用有界 | 无副作用，或副作用明确、可回滚、需授权。 | “自动修改所有文件”。 |
| 成本可估 | 有超时、预算、最大文件数、最大 token 或最大记录数。 | “一直搜索直到找到答案”。 |
| 可归因 | 知道由哪个 executor、哪个包、哪个版本执行。 | “系统生成”。 |

### 8.1 Move Manifest

```yaml
protocol: cyber-body.move/v0.1
id: scan-entrypoints
version: 0.1.0
kind: verifiable-move

verb: scan
slot: sense
summary: "扫描工作区中的入口点"

executor:
  preferred: tool
  fallback:
    - small_model
  requirements:
    tools:
      - ripgrep

input:
  schema:
    type: object
    required:
      - root
      - patterns
    properties:
      root:
        type: string
      patterns:
        type: array
        items:
          type: string
      max_files:
        type: integer
        default: 500

output:
  schema:
    type: object
    required:
      - entries
    properties:
      entries:
        type: array
        items:
          type: object
          required:
            - file
            - line
            - symbol
          properties:
            file:
              type: string
            line:
              type: integer
            symbol:
              type: string
            direction:
              type: string
              enum:
                - inbound
                - outbound
                - unknown

preconditions:
  - root.exists
  - permission.filesystem.read

postconditions:
  - output.entries[*].file is inside input.root
  - output.entries[*].line > 0

side_effects:
  filesystem_write: false
  network: false
  shell: true

limits:
  timeout_ms: 30000
  max_files: 500
  max_output_items: 2000

evidence:
  required:
    - command
    - exit_code
    - raw_match_count
    - truncated

failure:
  retry:
    max_attempts: 2
  on_missing_tool: "return capability_unavailable"
  on_too_many_results: "return partial_with_truncation_evidence"
```

这个 Move 小到可以由工具执行，小模型复核，大模型整合。

## 9. Move 类型库

先不要发明无限动作。第一版只保留少量可组合类型。

| Move 类型 | 输入 | 输出 | 适合执行者 | 例子 |
|---|---|---|---|---|
| `observe` | 资源位置、过滤条件 | 状态事实 | 工具/规则程序 | 读取文件列表、读取运行状态。 |
| `scan` | root、pattern、limit | 匹配项列表 | 工具/规则程序 | 扫描入口点。 |
| `extract` | 文本、schema | 结构化字段 | 小模型 | 从访谈中抽取痛点。 |
| `classify` | item、label_set | label | 小模型 | 给 Issue 打标签。 |
| `validate` | artifact、schema/rule | pass/fail + errors | 规则程序/小模型 | 检查 PRD 是否有验收标准。 |
| `compare` | A、B、criteria | diff | 小/中模型 | 对比两份报价。 |
| `rank` | candidates、criteria | 排序和理由 | 中模型 | 排序产品机会。 |
| `draft` | brief、constraints | 草稿 | 中/大模型 | 生成访谈脚本。 |
| `run` | command、args、sandbox | exit/status/log | 工具 | 运行测试。 |
| `write` | target、content、mode | patch/result | 工具 + 人类授权 | 写入文件。 |
| `ask_human` | question、options、context | decision | 人类 | 方向裁决。 |
| `audit` | move/evidence | finding | 大模型/规则程序 | 抽样审计小模型结果。 |

如果一个动作不能归入这些类型，先不要实现为 Move。

应先问：

```text
它是不是太大了？
它是不是缺少验证方式？
它是不是其实是 Operation 或 Capability？
```

## 10. 从复杂案例拆成能力包组合

### 10.1 老旧代码库恢复

应用层目标：

```text
把“不敢改”的代码库恢复成可观察、可验证、可安全推进。
```

能力包组合：

| 能力包 | 槽位 | 暴露 Move |
|---|---|---|
| `repo-sense.cap` | sense | `scan-files`、`scan-entrypoints`、`scan-configs`。 |
| `module-map.cap` | cognition | `summarize-module`、`classify-module-role`。 |
| `doc-code-drift.cap` | immune | `extract-doc-claims`、`validate-claim-in-code`。 |
| `test-runner.cap` | muscle | `run-test-command`、`locate-first-failure`。 |
| `risk-map.cap` | immune/lens | `classify-side-effect-risk`、`render-risk-lens`。 |
| `refactor-plan.cap` | cognition | `rank-safe-change`、`draft-change-plan`。 |

其中 `scan-entrypoints` 可以再拆：

```text
Operation: 构建入口地图
  Move 1: scan-files(root, include_globs)
  Move 2: scan-pattern(file_batch, patterns)
  Move 3: extract-entrypoint(match)
  Move 4: classify-entrypoint-direction(entrypoint)
  Move 5: validate-entrypoint-schema(entrypoint)
  Move 6: merge-entrypoint-list(entries)
  Move 7: audit-sample(entries, sample_size)
```

注意：`构建入口地图` 是 Operation，不是 Move。

### 10.2 研究论文推进

应用层目标：

```text
把散乱资料推进为可投稿论文计划。
```

能力包组合：

| 能力包 | 槽位 | 暴露 Move |
|---|---|---|
| `paper-sense.cap` | sense | `extract-paper-metadata`、`extract-method`、`extract-finding`。 |
| `literature-matrix.cap` | cognition/memory | `classify-paper-topic`、`merge-literature-row`。 |
| `citation-audit.cap` | immune | `validate-citation-support`、`find-unsupported-claim`。 |
| `argument-map.cap` | cognition/lens | `extract-claim`、`link-claim-evidence`、`render-argument-map`。 |
| `reviewer-redteam.cap` | immune | `draft-reviewer-attack`、`rank-weakest-point`。 |

`validate-citation-support` 的原子边界：

```text
输入：一句 claim + 一段 source excerpt + citation id。
输出：supported / partial / unsupported + 最多 3 条理由 + evidence span。
验证：输出必须引用 source excerpt 的 span，不能引用外部记忆。
```

### 10.3 电商运营

应用层目标：

```text
让小团队从订单、库存、客服、评价、内容的救火状态中解放出来。
```

能力包组合：

| 能力包 | 槽位 | 暴露 Move |
|---|---|---|
| `order-sense.cap` | sense | `import-order-row`、`detect-order-status`。 |
| `inventory-immune.cap` | immune | `detect-stock-conflict`、`validate-sku-mapping`。 |
| `customer-message.cap` | cognition | `classify-message-intent`、`extract-complaint-object`。 |
| `service-draft.cap` | cognition/muscle | `draft-reply`、`validate-service-boundary`。 |
| `ops-lens.cap` | lens | `render-daily-exceptions`、`render-boss-decisions`。 |

`draft-reply` 不是自动发送。

它必须拆成：

```text
Move 1: classify-message-intent
Move 2: retrieve-policy-snippet
Move 3: draft-reply
Move 4: validate-reply-boundary
Move 5: ask_human if refund/compensation/commitment
Move 6: send-reply only if authorized
```

## 11. 能力包组合规则

能力包不能随意互相调用。组合必须通过接口。

### 11.1 组合输入输出

能力包之间只能交换以下对象：

| 对象 | 用途 |
|---|---|
| `Observation` | 对环境、文件、用户输入、外部资源的事实观察。 |
| `Hypothesis` | 可被证据支持或反驳的假设。 |
| `MoveResult` | 单个 Move 的结构化结果。 |
| `EvidenceRef` | 指向证据的引用，不直接复制全部证据。 |
| `ArtifactRef` | 指向产物的引用。 |
| `DecisionRequest` | 需要人类裁决的问题。 |
| `PermissionRequest` | 需要授权的动作。 |
| `PainSignal` | 重复失败、异常成本、质量下降等疼痛信号。 |
| `MutationProposal` | 对能力包、Move、Lens、权限或流程的改进提案。 |

禁止能力包直接传递不可解释的大段上下文。

### 11.2 组合流程

```text
Promise
  -> select capability packages
  -> check compatibility
  -> mount context
  -> request permissions
  -> dry run contract tests
  -> compose Move graph
  -> execute Moves
  -> collect Evidence
  -> render Lenses
  -> request human decisions
  -> produce Artifact / MutationProposal
```

### 11.3 组合失败

组合失败不能静默降级。

必须返回：

```yaml
composition_failure:
  reason: "missing_permission | incompatible_schema | missing_executor | failed_contract_test | unresolved_reference"
  package: "doc-code-drift"
  required:
    - "filesystem.read:docs"
  available:
    - "filesystem.read:workspace"
  suggested_actions:
    - "grant docs read"
    - "disable doc-code-drift package"
    - "install compatible package version"
```

## 12. 权限是义体插槽的一部分

能力包默认没有权力。

权限必须按动作和槽位分配。

| 权限 | 默认 | 说明 |
|---|---|---|
| `filesystem.read` | 按 root 授权 | 只能读已挂载根目录。 |
| `filesystem.write` | 禁止 | 写入必须单独授权或沙盒。 |
| `network.read` | 禁止 | 外部访问必须声明域名、目的和数据边界。 |
| `network.write` | 禁止 | 发消息、提交表单、调用外部 API 必须高信任。 |
| `shell.run` | 禁止 | 只允许白名单命令；破坏性命令必须人工批准。 |
| `model.large` | 按预算 | 大模型调用需要预算和目的。 |
| `human.ask` | 限流 | 不能把用户变成审批机。 |
| `federation.share` | 禁止 | 共享给其他超级个体必须显式授权。 |

权限不是一次性设置。

它应该随信任梯度变化：

```text
observe -> propose -> draft -> sandbox -> low-risk-auto -> approved-agent
```

## 13. Evidence 协议

没有证据的能力包不能进入高信任等级。

每个 Move 至少产出：

```yaml
evidence:
  protocol: cyber-body.evidence/v0.1
  id: ev_20260510_001
  move_id: scan-entrypoints
  package_id: codebase-recovery
  package_version: 0.1.0
  executor:
    type: tool
    id: ripgrep
  input_ref: inputs/run-001.yaml
  output_ref: outputs/run-001.json
  status: success
  started_at: "2026-05-10T10:00:00+08:00"
  ended_at: "2026-05-10T10:00:03+08:00"
  side_effects:
    filesystem_write: false
    network: false
  verification:
    schema_valid: true
    postconditions_passed: true
    audited: false
  artifacts:
    - ref: artifacts/entrypoints.json
      type: application/json
  errors: []
```

证据的作用：

- 让 Lens 能解释状态。
- 让大模型能抽样审计。
- 让人类知道为什么可信。
- 让失败能变成 Pain Signal。
- 让能力包升级有依据。

## 14. Lens 协议

Lens 不是页面，它是对能力包状态的投影声明。

```yaml
protocol: cyber-body.lens/v0.1
id: risk-map
title: "风险地图"
reads:
  - evidence.type:risk
  - move.status
  - permission.requests
renders:
  sections:
    - id: critical_risks
      source: "risk.level == critical"
    - id: blocked_moves
      source: "move.status == blocked"
    - id: human_decisions
      source: "decision.status == pending"
actions:
  - id: approve_permission
    requires: human_approval
  - id: request_more_evidence
    creates: Move
```

Lens 只能读已授权的 evidence、artifact、decision、permission 对象。

它不能直接修改底层真相。

## 15. 能力包生命周期

```text
discover
  -> inspect manifest
  -> validate schemas
  -> check signatures/checksum
  -> install disabled
  -> run contract tests
  -> sandbox dry run
  -> request permissions
  -> enable observe/propose
  -> earn trust by evidence
  -> allow higher automation
  -> monitor pain signals
  -> propose mutation
  -> upgrade / rollback / uninstall
```

### 15.1 安装门槛

能力包必须通过：

- manifest schema 校验。
- move schema 校验。
- 权限声明检查。
- 依赖解析。
- contract test。
- 沙盒 dry run。
- 人类授权。

### 15.2 卸载要求

卸载必须处理：

- 生成的文件。
- 注册的 Move。
- Lens。
- 权限。
- 记忆。
- 证据引用。
- 其他包依赖。

不能删除历史 evidence，只能标记包已卸载。

## 16. 版本与迁移

能力包使用 SemVer：

```text
MAJOR：破坏 Move 输入输出、权限语义、证据结构、公共对象。
MINOR：新增兼容 Move、Lens、schema 字段。
PATCH：修复实现，不改变公共协议。
```

能力包必须声明：

```yaml
versioning:
  public_api:
    - capability.yaml
    - moves/*.move.yaml
    - schemas/*.schema.json
    - lenses/*.lens.yaml
  migration:
    from:
      - "0.1.x"
    to: "0.2.0"
    script: "./migrations/0.1-to-0.2.yaml"
  rollback:
    supported: true
```

如果不能降级，必须明确：

```yaml
rollback:
  supported: false
  reason: "evidence schema migrated irreversibly"
```

## 17. 能力包不是应用，应用是装配结果

以前的 20 个案例应重新解释为：

```text
应用案例 = Promise + 一组能力包 + 一组 Move Graph + 一组 Lens + 一组 Evidence
```

例如：

```yaml
application_assembly:
  id: old-codebase-recovery
  promise: "让失控代码库恢复为可安全修改状态"
  packages:
    - repo-sense@0.1.0
    - module-map@0.1.0
    - doc-code-drift@0.1.0
    - test-runner@0.1.0
    - risk-map@0.1.0
  move_graph:
    - scan-files
    - scan-entrypoints
    - summarize-module
    - extract-doc-claims
    - validate-claim-in-code
    - run-test-command
    - locate-first-failure
    - render-risk-lens
  human_decisions:
    - approve_test_command
    - choose_first_safe_change
```

系统价值在于：

- 能力包可复用。
- Move 可验证。
- 组合可解释。
- 权限可控。
- 证据可复盘。
- Lens 可替换。

而不是每次为一个大场景硬编码一个“助手”。

## 18. 原子动作进一步拆分示例

用户批评“可验证动作没有拆到原子或更细”。下面给一个具体拆法。

### 18.1 太粗的任务

```text
分析代码库，找出架构问题，并给出重构建议。
```

这不是 Move，也不是 Operation。

它至少是一个应用层 Promise。

### 18.2 拆成 Operation

```text
Operation A：构建代码结构地图
Operation B：构建文档-代码差异地图
Operation C：构建测试失败地图
Operation D：构建风险排序
Operation E：生成第一批安全修改建议
```

### 18.3 Operation A 拆成 Move

```text
A1 scan-files
A2 classify-file-kind
A3 scan-entrypoint-patterns
A4 extract-entrypoint
A5 validate-entrypoint-record
A6 merge-entrypoint-records
A7 audit-entrypoint-sample
A8 render-entrypoint-lens
```

### 18.4 Move A4 再拆到 Step 与 Assertion

Move：

```text
extract-entrypoint(match_line)
```

Step：

```text
1. parse file path
2. parse line number
3. parse symbol
4. infer entrypoint kind
5. produce entrypoint record
```

Assertion：

```text
file path is non-empty
line number > 0
symbol is non-empty
kind in enum
record validates against schema
```

注意：

- `Step` 不是独立调度单位。
- `Assertion` 是验证单位。
- `Move` 是最小可调度单位。

这能避免系统碎到不可管理，也避免任务粗到不可验证。

## 19. 第一批应内置的基础能力包

如果要做 MVP，不应从“创业助手”等大应用开始。

应先做 10 个底层义体包：

| 能力包 | 槽位 | 价值 |
|---|---|---|
| `file-sense.cap` | sense | 扫描、读取、分类、摘要文件。 |
| `schema-immune.cap` | immune | 校验输入、输出、证据和包协议。 |
| `evidence-store.cap` | memory/immune | 保存 Move 证据和产物引用。 |
| `human-decision.cap` | governance/lens | 生成决策请求、批量决策、记录裁决。 |
| `shell-muscle.cap` | muscle/governance | 在白名单和沙盒内执行命令。 |
| `text-extract.cap` | cognition | 抽取约束、事实、主张、行动项。 |
| `classify.cap` | cognition | 对小对象稳定分类。 |
| `lens-render.cap` | lens | 把证据、状态、决策渲染成人类视图。 |
| `permission-gate.cap` | governance | 权限申请、审批、撤销、审计。 |
| `package-loader.cap` | governance | 安装、校验、启用、禁用能力包。 |

这些才是“身体”的第一批器官。

应用包应在这些基础器官上装配。

## 20. 不做什么

第一阶段明确不做：

1. 不做通用“万能助手”。
2. 不直接内置 20 个应用场景。
3. 不把能力包等同 prompt 包。
4. 不允许无 schema 的能力进入高信任等级。
5. 不允许能力包绕过权限系统。
6. 不把 Lens 做成状态真相源。
7. 不把 Step 级别暴露成调度单位。
8. 不把大模型输出当证据。
9. 不默认联网、写文件、发消息。
10. 不把用户变成持续审批机器。

## 21. 下一步应产出的文件协议

后续应继续补充：

1. `capability.schema.json`：能力包 manifest schema。
2. `move.schema.json`：Move manifest schema。
3. `evidence.schema.json`：Evidence 对象 schema。
4. `lens.schema.json`：Lens manifest schema。
5. `permission.schema.json`：权限请求和授权 schema。
6. `assembly.schema.json`：应用层组合 schema。
7. `mutation.schema.json`：能力包改进提案 schema。

最小代码验证不应先做 UI。

应先做：

```text
读取一个 capability.yaml
  -> 校验 manifest
  -> 校验 moves
  -> 检查权限
  -> 运行一个无副作用 Move
  -> 产出 Evidence
  -> 用 Lens 渲染状态
```

这个闭环跑通，才说明“装载义体的身体”开始存在。
