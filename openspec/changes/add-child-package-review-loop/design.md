## Context

当前 AI 沙盒已能执行根业、登记分业、调度活跃前沿子业、提交结构化子业果包，并记录父业重评估。但子业果包仍只是 `reviewing` 状态下的候选相；父业只能看到“有候选果包回流”，不能看到“此果包已由独立验收位接收，可以作为父业可消费材料”。

真相源要求候选隔离、完成权归属和验收失败回流。子业执行者不能自己接收果包；会被父业消费的子业结果需要独立验收。第一版不做完整人类裁决和长期治理，只补齐低风险、可逆、结构化果包的最小 AI 验收闭环。

## Goals / Non-Goals

**Goals:**

- 对已提交的子业果包发起独立验收 provider 调用。
- 验收响应使用结构化 JSON，包含 `accept` 或 `repair`，并提供可量化检查、证据和父业消费摘要。
- `accept` 时由运行时服务接收子业候选果包和证据，使子业进入 accepted。
- `repair` 时拒收当前候选，创建修复子业，执行修复请求，重新提交修复果包并再验收一次。
- 每一步写入 JSONL 和中文可读日志，并进入业树镜像。
- 父业重评估继续只记录，不自动接收父业或根业。

**Non-Goals:**

- 不实现无限修复循环；第一版最多一次修复再验收。
- 不实现高价值人类裁决 UI；高价值判断仍只显影为开放缺口或后续业。
- 不新增数据库表或持久化状态机类型。
- 不自动把所有已接收子业整合为父业最终成果。
- 不硬编码小说、人物、内丹法或任何业务场景。

## Decisions

1. **验收位作为独立 provider 调用，而不是复用子业执行响应。**

   子业执行位负责产出候选果包；验收位只判断候选是否满足子业验收契约和父业消费要求。这样保留“执行者不能自行验收”的边界。

2. **验收响应只允许 `accept` 或 `repair`。**

   第一版不直接引入 `reject` 终局，因为多数 AI 生成失败应先给一次修复回流机会。真正废弃、仲裁或人类裁决后续再作为独立能力进入。

3. **代码守门器只执行结构化动作，不判断审美价值。**

   AI 验收位给出候选判断和证据；代码只检查 JSON 结构、动作枚举、检查项和证据字段，然后通过 `RuntimeService.accept_candidate` 或 `reject_candidate` 执行状态迁移。

4. **修复业挂在被打回子业下面。**

   修复是针对子业果包缺陷的局部工作，应该成为原子业的子业，而不是新的根业或父业兄弟。修复果包重新提交到原子业，让父业消费点保持不变。

5. **父业消费以重评估日志显影。**

   复用 `TreeService.reevaluate_parent()` 的 `accepted_results`。验收通过后再次记录父业重评估，让日志能看到哪些子业已 accepted，哪些仍 unresolved，开放问题是否仍存在。

## Risks / Trade-offs

- [风险] AI 验收仍是弱证。→ 日志明确记录 provider 调用和弱证来源；高价值/不可逆任务后续必须接人类裁决或外部证。
- [风险] 一次修复不够。→ 第一版限制一次修复以防调用失控；失败仍记录为打回和未完成，不伪装通过。
- [风险] 修复业 accepted 可能被误解为父业完成。→ 只接收原子业果包，不接收父业或根业；父业重评估只记录。
- [风险] 验收 JSON 非法。→ 记录验收失败，不改变子业候选状态，不继续父业消费。
