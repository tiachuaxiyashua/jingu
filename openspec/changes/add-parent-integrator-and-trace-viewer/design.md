## Context

当前运行链路已经具备根业候选、分业登记、前沿子业调度、子业果包提交、独立验收、修复回流和 accepted 子业重评估。缺口是父业没有把 accepted 子业果包整合成父业自己的候选成果，因此业树还停留在“局部供料已接收”，没有进入“上层业消费供料继续成事”。

现有网页 viewer 能按 JSONL 重放业树节点，但它的详情维度不足：用户不能按步骤看到 provider 输入、provider 输出、运行步骤、果包、验收判断、修复指令、父业重评估和状态变化之间的对应关系。作为镜相，它必须帮助人看见证和卡点，但不能反向改变运行库。

## Goals / Non-Goals

**Goals:**

- 在子业 accepted 后触发父业整合器，生成父业整合候选和证据。
- 父业整合器只消费 accepted 子业结果，未验收候选不得进入整合输入。
- 父业整合响应必须结构化，包含整合结论、父业候选正文、已消费子业、证据、开放缺口和后续分业建议。
- 父业整合候选提交到父业，但不自动接收父业或根业。
- viewer 能逐步展示每一步输入、输出、动作、状态变化、证据和业树变化，并支持按关键步骤跳转。

**Non-Goals:**

- 不实现父业最终自动验收或根业自动完成。
- 不实现复杂多父业调度、并行整合或冲突仲裁。
- 不实现后端服务或数据库查询界面；viewer 仍是静态只读页面。
- 不把 viewer 投影作为运行库事实来源。

## Decisions

1. **父业整合器只在存在 accepted 子业结果时运行。**

   这样防止未验收候选被父业消费，遵守候选隔离律。没有 accepted 子业时记录跳过，便于日志定位。

2. **父业整合候选提交到父业，不自动接收。**

   父业整合器是行者，只能提交候选果和证，不能宣告父业完成。父业候选后续仍要走校验、修复和验收路由。

3. **整合器可提议后续分业，但仍走既有分业守门器。**

   父业整合中暴露的新缺口不能直接变状态，应由 split proposal registration 经代码守门登记。

4. **viewer 构建事件 trace 模型。**

   在现有业树投影外，增加每个事件的语义分类：输入、provider 请求、provider 响应、状态迁移、候选/证据、验收/修复、整合、清理。每一步右侧展示“输入/输出/动作/证据/状态变化”，让用户按下一步看到流程如何移动。

5. **viewer 不依赖业务硬编码场景。**

   只根据 event_type、job_tree_action 和 data 字段分类，标签可维护，但不写小说、人物或内丹法场景规则。

## Risks / Trade-offs

- [风险] 父业整合器仍是 AI 弱证。→ 只提交候选和证据，不自动接收父业。
- [风险] 真实模型 JSON 不稳定。→ 增强结构化提示、解析失败记录为跳过或拒绝，不污染状态。
- [风险] viewer 信息过载。→ 分区显示输入/输出/动作/证据，默认展示当前步骤摘要，原始 JSON 保留在独立区域。
- [风险] viewer 分类规则滞后于新事件。→ 使用通用 fallback，未知事件仍显示原始数据并进入时间线。
